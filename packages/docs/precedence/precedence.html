Precedence And Types

Why spell's grammar needs binding power and datatypes, what breaks today, and what to build.

Written for: Owen, and any agent about to change the parser's rules Status: being revived 2026-10-03 as epic precedence-and-types; nothing built yet. A design doc until then, rewritten as built at the end. Researched on: branch ts-conversion, 2026-09-30; re-checked 2026-10-03: all probes unchanged. Every "today" output was produced by running the parser, see Sources and experiments.
  • The parser can't say what an expression is (its type) or how tightly it binds (its precedence), so every rule guesses from shape.
  • All four language goals trace back to that one gap: paren-free signatures, of in method names, multi-word properties, real precedence.
  • Proposal: plumb two facts through every match, bindingPower and datatype.
    • Expressions parse by precedence climbing with bounded operands, plus a cheap bounded backtrack.
    • Members, signatures and call sites become lookups over types.
  • Two ideas from review are folded in: exclusive lists as a property of a list type, and a TypeScript backend the editor compiles a second time. The TypeScript check is now an epic of its own, later.
  • Types are named in spell's words everywhere, never JavaScript's.

Eight of them, each with what the parser does today.

  • A rule whose syntax ends in {expression} gives that slot the rest of the line, operators included.
  • Choice returns exactly one candidate and Sequence accepts it or fails. The candidate that would have worked is never built.

/** `expression`:  a term, then every suffix that binds tighter than `minBP`. */
class expression extends P.OperatorExpression {
  @proto static atoms = "term"
  @proto static suffixes = "expression_suffix"

  parse(scope: P.Scope, tokens: P.Token[], minBP = P.Operand.currentBP): P.Match | undefined {
    let lhs = scope.getRuleOrDie(this.atoms).parse(scope, tokens)
    if (!lhs) return undefined
    const suffixes = scope.getRuleOrDie(this.suffixes)
    for (;;) {
      const rest = tokens.slice(lhs.length)
      // only suffix rules with `bindingPower > minBP` may match here
      const suffix = P.Operand.boundedBy(minBP, () => suffixes.parse(scope, rest))
      if (!suffix) return lhs
      // one match;  its AST is `suffix.rule.compileAST(lhs.AST, rhs.AST)`, exactly as today
      lhs = this.combine(lhs, suffix)
    }
  }
}

// an infix suffix's syntax:  `(operator:and) {expression:operand}`
//   its rhs parses with `minBP = 6`, its own `bindingPower`, so `x and y is 1` is `x and (y is 1)`
//   and `a and b and c` is `(a and b) and c`:  left-associative, because the test is strictly greater
  • Rulex gets {x:operand}: "an expression bounded by MY bindingPower". {expression} still means a full one.
  • The bound is a module-level value, set and restored by Sequence.parse(): the same trick as allowRunOut in Sequence.ts, two assignments on the hot path.
  • Completion keeps working: the loop records expectations as Choice and Repeat do, and the memo key includes the bound.
  • Each position is parsed once per bound, so this does less work than today's double parse.
  • Choice.parse() already computes every candidate. With more than one, it keeps them on the winner, best first.
  • When a later child of a Sequence fails, the sequence resumes from the previous child's next candidate.
  • No re-parsing. At most one retry per candidate. Nothing allocated when there is one candidate, the common case.

Binding power fixes shape. The type problems need the parser to know what an expression is.

  • It is the rule the codebase already follows for scopeVar: look it up WHILE PARSING, stash it on the match, never touch scope from getAST().
  • Rule.getDatatype(match), memoized as match.datatype. Default: the rule's existing datatype static.
  • No type yet is undefined, and is compatible with everything. Nothing that parses today stops parsing.
  • literals, from their rule
  • a known variable, from its scope record
  • a new card, a new list of cards
  • the X of Y and its X, from the member found on Y's type
  • a method call, from its return type
  • comparisons, aliases, and / or / not: choice
  • arithmetic: number, or text when a side is text
  • list rules: the item type, the list's type, or number
  • method arguments: (a card), (x as text), with … as …
  • this and it inside a method, from its owner
  • new variables from set, get and X is Y
  • for each card in the deck and where, from the list's item type
  • on card-click with a card
  • a pile is a list of cards records the item type on Pile
  • TypeScope.getMember(words) walks the super-type chain. The code moves from the language server, which then delegates.
  • Methods get real records, P.ScopeMethod: words, output name, parameters with types, return type, where declared.
  • These are the facts SPELL: DECLARES already writes, so an imported project rebuilds them.
  • thing, list, app, text, number, choice, date become real types in the root scope.
  • Members come from one data table per type: words, datatype, parameters, how it compiles.
  • So the same words mean different things on different types: the length of the name is .length, the length of the deck goes through the list helper.
  • Adding a built-in type is one table entry plus its runtime class. The Type Explorer's pack is generated from the same table.
  • Today one idea has several spellings: the AST says "string", rules say text; a list literal's rule says "array"; choice maps to boolean in one table while as yes or no compiles to 'choice'.
  • The runtime already speaks spell: spellCore.typeOf() turns string into text, boolean into choice, array into list.
  • The parser uses exactly that vocabulary wherever a type is stored: scope records, declarations, AST.
  • JavaScript's words are accepted only where a user WRITES them.

The note. "Since we have our own List type, what if we had an exclusive list concept which says an item can only be in one object of my type at once, and does the add-removes-from-previous-parent that we do manually with pile? This should work for subclasses too, and deck would need to be a different descendant path so a card can be part of a deck AND part of one of the piles."

  • Words to bikeshed: a pile is an exclusive list of cards.
  • Records exclusive on Pile.
  • Every subtype inherits the FAMILY rooted at Pile: tableau, foundation, stock-pile, discard-pile.
  • a deck is a list of cards is another family, or none. So a card can be in the deck and in one pile.
  • The item type gains a read-only member named after the family root: the pile of a card.
  • It is the pile holding the card, or nothing.
  • It is declared on Card by Pile's line, so go-to-definition lands there.
  • It is written into SPELL: DECLARES, so an importing project rebuilds it.
  • This is what the type plumbing is for: one line adds a fact to TWO types.
  • List.add(), addAtPosition(), removeItem() and clear() consult the list's family.
  • One WeakMap per family maps an item to its owner.
  • Adding removes the item from the previous owner of the same family first.
  • The derived member reads the map, reactively.
  • Scratch results from map() and filter() must NOT take ownership: one more reason for the debt item that makes them plain lists.
  • Pile.spell's to move and its bookkeeping go away. add the card to the pile does it.
  • "In a deck and in a pile" is the default: a family is the exclusive type and its subtypes, nothing to say out loud (D7).
  • remove the card from the pile leaves a card ownerless: a card on the table (D8).
  • a copy of the pile and where results are plain lists, owning nothing (D8).

From review: have the compiler emit TypeScript, and compile it a second time. The second step is a service the EDITOR has; a runner only ever loads the optimized JavaScript.

  • The spell compiler writes typed .ts of the shapes it emits today: accessor pairs and spellCore.element() calls, with types from each match's datatype.
  • A second step checks it, then strips the types: the JavaScript programs run on, as today.
  • That step is assumed available wherever spell is COMPILED: the app's editor, <spell-editor>, the language server. It may be expensive and in memory.
  • It is never in a runner: the app's run pane, VS Code's runner and <spell-app> load plain JavaScript, as today.
  • Two payoffs:
    • a second opinion on every line the parser wrote
    • type answers the parser doesn't have

/** Emitted text, plus which AST node wrote each range of it. */
type Emitted = { text: string; spans: EmittedSpan[] }
type EmittedSpan = { start: number; end: number; node: P.ASTNode }

class ASTInfixExpression extends ASTExpression {
  // today:  a string, and where it came from is lost
  compile(): string {
    return `${this.lhs.compile()} ${this.operator} ${this.rhs.compile()}`
  }

  // proposed:  the same one-liner;  the tag asks each node for its own `emit()`, shifts its spans
  // by where it landed, and adds one span for `this`
  emit(): Emitted {
    return P.emit(this)`${this.lhs} ${this.operator} ${this.rhs}`
  }
}

/** Innermost node whose output covers `offset`:  its `match` is a range in a spell file. */
function nodeAt(emitted: Emitted, offset: number): P.ASTNode | undefined {
  let found: EmittedSpan | undefined
  for (const span of emitted.spans) {
    if (span.start > offset || span.end <= offset) continue
    if (!found || span.end - span.start <= found.end - found.start) found = span
  }
  return found?.node
}

type TypeScriptService = {
  /** Replace the files it knows:  the emitted `.ts`, `@spell/core`'s types, imported projects' types. */
  setFiles(files: Record<string, string>): void
  /** Type errors, as offsets into the emitted files. */
  semanticDiagnostics(): Promise<TypeScriptDiagnostic[]>
  /** Type of the expression at `offset`, in TypeScript's words, e.g. `"Card | undefined"`. */
  typeAt(file: string, offset: number): Promise<string | undefined>
  /** Plain JS:  types stripped, nothing else changed. */
  lower(files: Record<string, string>): Promise<Record<string, string>>
}

/** Editor only:  runs after the spell compile, before anything is saved or run. */
async function checkAndLower(project: SP.SpellProject, service: TypeScriptService): Promise<CheckedOutput> {
  const emitted = project.emitTypeScript() // one `.ts` per spell file, each with its node => output-range spans
  service.setFiles({
    ...emitted.files,
    "/spell-core.d.ts": SPELL_CORE_TYPES, // generated from `packages/core/src/` when the editor is built
    ...project.importedTypes() // an imported project's `<Project>.compiled.ts`, saved beside its `.js`
  })

  const problems: SpellProblem[] = []
  for (const diagnostic of await service.semanticDiagnostics()) {
    const node = emitted.nodeAt(diagnostic.file, diagnostic.start) // innermost AST node that wrote that range
    if (node) problems.push({ match: node.match, message: inSpellWords(diagnostic, node) }) // a SPELL range
  }

  // what every runner loads:  plain ES modules which import only `@spell/...`
  const javascript = await service.lower(emitted.files)
  return { problems, javascript }
}
