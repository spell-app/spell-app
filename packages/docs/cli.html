spell Command Line

spell, packages/cli: compile, check, explore, run, test and debug spell projects from a terminal, seeing exactly what the editor sees.

  • Written for: people and agents working on spell or its tools
  • Status: built; not yet reviewed by a person
  • Built from the plan doc epics/cli-additions/cli-additions.html (2026-10-01); every claim here is covered by packages/cli's tests -- see Sources
  • One command, spell, runs spell's SOURCE through tsx: no build step, so it's always the working copy.
  • Projects load the language server's way (SpellDiskWorkspace), and questions go to its SpellLanguageService and ScopeExplorer: what spell says, the editor says.
  • Commands: compile, check, describe, explore, watch, run, test, format, projects, speed, parse, repl, explain, new, icons, serve, help.
  • No target: the project here -- or, outside one, an autocompleting prompt. A UI project's run opens in your browser.
  • Output to stdout, progress and screens to stderr; exit codes 0 fine, 1 the spell has errors or a test failed, 2 the command line is wrong.
  • yarn cli:install in packages/cli, then spell --help.

Targets everywhere: a .spell file, a project folder, @workspace (the project here), @library/cards, a full id, or a whole root like @examples. None: see Target prompt.

command does
compile writes <Project>.compiled.js, and with no errors its scope pack; --stdout, --force
check errors as path:line:col message; --json
describe the Type Explorer as text, or one thing in it
explore full-screen Type Explorer; reloads as files change; e edits a description
watch recompiles on save; rebuilds watched importers; --test, --check-only
run / test run under node -- a UI project then in your browser (--browser, --no-browser); test --name, test --watch
serve the spell app -- editor + /api, which saves to disk -- opened on the target; --port, --headless
icons find ui icons by name, alias or keyword; --open: a gallery in your browser
format whitespace, as Format Document; --check; never in projects/test/
projects roots, or one root's projects, with the names to type
speed parser speed test as a table; --against HEAD adds Previous and Change
parse / repl a line's match tree and javascript; --in a project's scope
explain rules a word names or starts; --in: what a project declares by that name
new project.json + a starter .spell, in @user or --in
help the commands, or one command's options

A command is one function; long-running work happens in child processes or on Ink screens.

bin/spell.mjs registers tsx, imports src/main.ts main.ts silences console.* first, then commander picks the command <name>Command (session, args, options) => exitCode; CliSession owns the workspace, language service and explorer
  • Child processes, src/runner/: runProject.ts (run / test), speedTest.mts (speed). They never import $/cli's values.
  • Ink screens, src/ui/: always patchConsole: false.
  • <Project>.scopes.js: the Type Explorer's data for a page with no parser, e.g. <spell-app>.
  • Written after a CLEAN compile -- compiled, no errors -- by the language server, yarn scopes, spell compile and spell watch, all through SpellDiskWorkspace.writeScopes().
  • Checked: spell compile on the three example projects rewrote their checked-in packs unchanged.
  1. Each run is a fresh node process running SP.spellParser.speedTest(): a warm-up, then 20 timed passes.
  2. --against <ref>: a temp git worktree of the ref, our node_modules linked in, the runner COPIED in, run there; removed afterwards, links first.
  3. The two sides take turns, run by run, so a busy moment hits both alike.
  4. A side's runs combine as the mean of their averages, the lowest min, the highest max; with 3+ runs one fluke (an average over 1.25x the median) is dropped.
  • parse / repl parse in a scope of their own, inside the project's with --in: its types and phrases are known, but nothing typed lands in it.
  • No rule given: statement, then expression; several lines: block. repl commits each line, so later lines know what it declared.
  • explain: rules by name or by the first word of their syntax; declarations as the editor's hover, less its first section (the declaring rule).

/**
 * A fresh scope to parse lines in:  inside `project`'s, so its types and phrases are known -- or, with none, a bare
 * one with only spell's own rules.
 */
export function lineScope(project?: SP.SpellProject): P.Scope {
  if (!project?.scope) return SP.spellParser.getScope("cli")
  return new P.ProjectScope({ name: "cli", parentScope: project.scope })
}
  • fs.watch() on each project's folder: .spell, .css, project.json. The kind of change comes from what's on disk, not the event: macOS reports a save as a rename.
  • A watched importer rebuilds from scratch after a project it imports, as if its project.json changed: a compiled import's declarations are only read on a full parse.
  • --test runs the tests in a child process, capturing its output: failures show under the project's row.
  • explore reloads the same way, keeping what's open and the cursor, by path.
  • No target, in a project's folder or below: that project, for every command.
  • Outside one, in a terminal: a prompt that completes like a shell -- Tab completes a root (@examples/), then a project, then "entire project" or one of its files. Piped: an error.
  • The last 3 picks come first, from packages/cli/.recent-targets.json (gitignored, per checkout).
  • Keys arriving together -- typed while it's busy, or pasted -- are split and taken one at a time: Ink only names a key that arrives alone.
  • serve.ts: a small server on localhost, answering only its routes; SPELL_NO_BROWSER=1 prints the URL instead of opening a browser.
  • icons --open: a gallery page of the packs' SVGs, with a filter box; click to copy a name.
  • run: the child tells spell over IPC that the project tried to show a UI; then a page with app's <spell-app src=...> serves the project as compiled for this run, its scope pack, and its imports. dist-element/ is built first if missing.
  • serve: app's own yarn start:dev (vite) and yarn start:server (express), each in its own process group, stopped together; a busy port is refused.
  • The language server's workspace, not a parallel loader: so the command line and the editor can't disagree.
  • speed copies its runner into the other checkout: the $/ aliases only resolve inside a tree, so a script outside it can't import spell.
  • new writes its own files: projectUtils.createProject() goes through getIndex(), which adds an Untitled.spell. Default folder: @user.
  • Test name filter is --name: test takes several targets, so a positional name couldn't be told from one.
  • explore edits inline, one line: quick for the common case; several-line descriptions go to the editor (o).
  • Never writes into projects/test/: test projects stay frozen -- format and e refuse, tests use temp copies.
  • Browser runs use <spell-app src=>, not the app server: compiled JS and its scope pack, served beside each other -- no /api to run.
  • serve isn't yarn start: that runs yarn install and yarn stop, which would stop other checkouts' servers.
  • Icon keywords match a word's start: names and aliases anywhere, so bell finds dumbbell but not brain by its keyword cerebellum.
  • It runs spell's WORKING COPY: a half-done change in lsp/src/ or SpellProject can break spell with nothing in spell noticing.
  • speed --against links today's node_modules into the old tree, and needs a ref from the monorepo on: a ref with different dependencies may not run.
  • format trusts formatting() to change whitespace only.
  • repl's live screen is tested through ink-testing-library; piped mode end to end.
  • explore's e: one-line descriptions only.
  • watch sees only what it watches: an imported project not watched doesn't rebuild its importer.
  • Under node, run skips what needs a browser, e.g. starting a UI; other browser-only code throws. In the browser it serves what was compiled at the start: no live reload.
  • @examples/Solitaire-import deals nothing, in the browser and in the app alike: a known spell runtime problem with importing an app project, not the CLI's.
  • serve opens only projects in the app's roots; others open the chooser.
  • spell lsp, with the VS Code extension spawning it
  • a single-file bundle, so it installs without a checkout

  • Unit tests beside each module, e.g. packages/cli/src/commands/speedCommand.test.ts; screens through ink-testing-library, e.g. packages/cli/src/ui/ReplScreen.test.tsx.
