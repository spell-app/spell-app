  • Taken with Owen: @spell-app/ui from SOURCE; CLEAN BREAK in spell JSX (no SUI.*, raw <ui-*> tags, class=); INCREMENTAL phases, each green, stop for review after each.
  • Solid 2 facts that force the design (measured):
    1. writes are staged: read right after write returns OLD value until microtask / flush(). Spell is imperative (set then print must be exact), so spell state can't be Solid signals
    2. write feeding pending async is HELD with its whole batch (entanglement): even flush-per-write can read stale
    3. no writes in owned scope (dev throws; untrack doesn't exempt); no mutable store
    4. one Solid per page; one uncaught error halts the page's whole scheduler
  • Spell cells: each instance keeps a Map record, the ONLY truth, read and written synchronously. ~200-line sync core (cells + memoized derived values, equality cutoff); one enableExternalSource bridge tells Solid; spellCore.flush() = pending derived checks, then Solid's. Prototype: experiments/spell-cells.core.ts.
  • Accessors for Things, Proxy only for class-less data (editor's nested plain data, JSON): a Proxy costs ~2.5-6x on every access.
  • Decorators for hand-written classes: @prop({ type, default }) accessor, @derived, @thing (runs create() after all field initializers). Prototype: experiments/decorators.ts.
  • Compiled output: no decorators (runs from a blob: URL); accessor pairs + class schema; JSX emits THUNKS for every non-literal prop / child; imports only @spell-app/core, whose element() adapts onto @solidjs/h.
  • Bundles: Solid + @spell-app/ui in ONE shared spell-solid.js across element / runner / editor builds, never in spell-runtime.js; an import-map <spell-app> variant for host pages already running Solid.

Q1 Solid version: bump ui to rc.13 first, or start app on rc.11? → D1

One Solid per page: app must run the SAME Solid as @spell-app/ui and its fork solid-element. Today both pin rc.11; rc.13 is current. Every experiment in packages/docs/solid/experiments/ behaved the same on rc.11 and rc.13; public API unchanged.

A. Bump ui to rc.13 first (recommended)
  • own phase before tooling: bump ui + solid-element, run ui's yarn review, visual tests, fork tests
  • app starts on rc.13 and never moves twice
  • cost: one extra phase; touches ui, which another session may be working in
B. Start app on rc.11
  • no ui changes now; start app work at once
  • later bump moves ui AND app together, re-running both suites
  • cost: migrate onto an older RC, bump mid-migration
D1 Bump ui to rc.13 first: P2, before Tooling (Q1)

App never moves Solid twice; ui's suites catch RC behaviour changes before app depends on them.
