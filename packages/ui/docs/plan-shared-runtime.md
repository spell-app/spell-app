# Plan: shared-runtime packaging for both spikes + a forked Solid element layer

(The approved master plan now lives in [the plan](plan.md);  this file is the plan for this step only.)

> NOTE (2026-10-09):  `@spell-app/solid-element`, the forked element layer this plan made ("the fork" below), is gone:
> epic `spell-element` folded it into `src/elements/`.

## Context

- Owen will build the spell app on Solid 2.
  - If `@spell-app/ui` components share the app's copy of Solid, the Solid runtime costs nothing extra per page.
  - And app signals / context can flow straight into components.
- Today neither spike shares anything:
  - every build bundles its base library (Lit 7.5 KB, Solid 28 KB gzip) and our element core into each measured widget
  - smoke pages import `src/` through the dev server, never `dist/`
  - so every family carries a ~15 KB (Lit) / ~43 KB (Solid) "floor"
- Goal 1, both spikes:
  - the base library becomes a peer dependency, externalized
  - our element core becomes ONE shared chunk
  - each widget's cost is just its own classes + CSS + vocabulary
- Goal 2, Solid only:  replace `@solidjs/element` + `component-register` with our own fork.
  - It fixes the gotchas the spike works around.
  - It's written so each fix could become an upstream PR.
- Goal 3, both spikes:  when a component fails, fall back to a NATIVE element with equivalent function,
  so a page degrades instead of losing controls.
  - E.g. a failed `ui-button` becomes a working `<button>`.
- Goal 4:  the two REPORTs become directly comparable.
  - same sections, same measurements, same table headers
  - numbers generated by the same scripts
- Outcome:
  - Both REPORTs and [Lit vs Solid](spike-lit-vs-solid.md) get a "shared runtime" section, with apples-to-apples numbers.
  - The Solid spike's element core shrinks, by deleting its workarounds.

## What the exploration found

- Build / measure (both spikes):
  - No `external`, no `peerDependencies`.
    Solid groups `solid-runtime` into its own chunk only to count it.
  - The two measures aren't comparable:
    - Lit's `measure.ts` builds in memory and buckets modules by id (it already has an "own" measure).
    - Solid's `demo/measure.ts` regex-parses `dist/`, and has no "own" measure.
  - Smoke pages load `/src/index.ts` or `$spike/index` from the dev server.
    `duplicate-lit.html` and the Solid 1.9 host page test two runtimes.
- The Solid element layer:  `@solidjs/element` (84 lines, in `node_modules`) + `component-register` (287 lines).
  Both MIT, by Ryan Carniato.
  - Every spike workaround traces to a line:
    - bare booleans parse false (`component-register.js:60`)
    - `true` reflects `"true"` (:69-71)
    - pre-upgrade props dropped (:122)
    - `removeAttribute` ignored on bare booleans (:161)
    - per-instance accessors shadow `style`/`hidden` (:41)
    - microtask reflection guard (:70/73)
    - teardown on reconnect (:146-155)
    - no `BaseElement`/registry/shadow options in `customElement()` (element :77-83)
    - owner lookup stops at shadow roots (element :19-31)
  - Upstream `component-register` has matching open issues, and unreviewed PRs (#30, #39):
    - #15 formAssociated
    - #20 removed-attribute default
    - #5 reconnect
    - #38 `id`
    - #40 underscores
  - NOT fixable by a fork (Solid 2 itself):  eager memos, no signal writes in owned scopes, two-arg `createEffect`.
    A fork can only hide some of them behind defaults.

## Approach

### 1. Shared-runtime packaging (both spikes)

- `package.json` in each spike:
  - The base library moves to `peerDependencies` (+ `devDependencies` for tests):
    `lit`;  or `solid-js`, `@solidjs/web` and the fork (below).
  - `exports`:  `./core` (shared element core), `./<component>` per family, `./index`.
  - `sideEffects`:  component entries + CSS.
- Vite library config (`spike/lit/vite.config.ts`, `spike/solid/vite.config.ts` + `vite.shared.ts`):
  - `rolldownOptions.external` as a function, subpath imports included:
    - Lit:  `/^lit(\/|$)|^lit-(html|element)(\/|$)|^@lit\//`
    - Solid:  `/^solid-js(\/|$)|^@solidjs\//` + the fork
  - A new `core` lib entry, so component entries import it instead of inlining it.
    It exports the spike element core AND the foundation it uses:
    `$/ui/elements`, `$/ui/vocabulary`, `$/ui/util`, the `$/ui/runtime` loader, `Icons`.
  - Keep the `UIRuntime` chunk and icon data as lazy dynamic chunks (unchanged).
- One shared measurer, so numbers are comparable:
  `spike/shared/SpikeMeasure.ts` (a class), used by both spikes' `measure` scripts.
  - An in-memory `vite build` (Lit's approach), bucketing modules by id:
    - `library`:  external, measured separately by bundling the peer set once
    - `core`, `runtime (lazy)`, `icons (lazy)`
    - per family, `own`:  classes + `ui-<name>.css` + vocabulary
  - Min + gzip level 9 with esbuild, the same for both.
  - It reports:
    - library, core, own per family
    - "page with one button":  library + core + button
    - "all eight":  library + core + Σ own
    - "app already ships the library":  core + Σ own
  - It writes `measure-results.json` per spike.
- Import-map smoke pages, SHARED by both spikes (`spike/shared/frameworks/`), so both run the identical checks:
  - `yarn build`, then serve the spike's `dist/` + a vendored copy of its peer set,
    so pages run offline and deterministically.
    The vendored copy is a tiny `vendor` build of the `lit` / `solid-js` subpaths used.
  - One page per host (`vanilla`, `react`, `vue`, `solid`), + the existing `check.js` round trip.
    - The smoke runner writes the spike's own `<script type="importmap">` into each page,
      mapping `lit` / `solid-js` / `@solidjs/web` / `@spell-app/ui/…` to that spike's files.
    - React and Vue still come from esm.sh.
  - Solid 2.0 everywhere:  the `solid` host page is a small Solid 2 app, used for BOTH spikes.
    - It's `spike/shared/frameworks/solid/app.tsx`, compiled once with the Solid 2 plugin,
      with `solid-js` / `@solidjs/web` external.
    - On the Solid spike it also proves:
      - one `solid-js` module instance shared by app and components (assert a module-level identity)
      - app context reaches a component (owner adoption)
      - an app signal drives a component prop with no glue
      - `ui-change` updates the app signal
    - On the Lit spike it's the plain "Solid 2 app consuming custom elements" check.
  - Compatibility checks, clearly labelled as such in page title and report:
    - `compat-solid-1.9.html`:  an older Solid host, alongside our Solid 2 copy
    - `compat-duplicate-lit.html`:  a second Lit copy, loaded by full URL
    - Nothing else uses Solid 1.x.

### 2. Forked Solid element layer:  `spike/solid-element/` (`@spell-app/solid-element`)

- A new self-contained TypeScript package.
  - MIT, with a header crediting `@solidjs/element` / `component-register`.
  - Linked into `spike/solid` with `"@spell-app/solid-element": "link:../solid-element"`.
- Its API is a SUPERSET of `@solidjs/element`, so it could replace it upstream.
  - The same `customElement(tag, props, Component)`, `withSolid`, `noShadowDOM`, `getCurrentElement`.
  - Additions go in an optional 4th `options` argument.
- Fixes, each isolated in its own module + test, so it maps to one upstream PR:
  1. Options:  `{ BaseElement, registry, shadowRootInit: { mode, delegatesFocus } | false, formAssociated, internals }`.
     The package defines the class itself (no capturing-registry trick).
  2. Properties:
     - accessors on the PROTOTYPE
     - the standard upgrade step:  own properties captured in the constructor, re-applied through setters
     - `"key" in el` true before connect
     - a dev error for keys that shadow `HTMLElement.prototype` members, unless renamed via `property`
  3. Per-prop `{ attribute, type, converter: { fromAttribute, toAttribute }, reflect }`.
     - The default boolean rule:  present / `""` → true, removed → false, `true` reflects as `""`.
     - JSON parsing only for `type: Object | Array`.
  4. Attribute changes:
     - `attributeChangedCallback` always applies removals.
     - Change callbacks receive the source:  `"attribute" | "property"`.
     - Reflection is synchronous, with a re-entrancy guard (no microtask window).
  5. `ElementInternals`:  `element.internals`, and form hooks registered during setup:
     `onFormReset / onFormDisabled / onFormStateRestore / onFormAssociated`.
  6. Lifecycle:
     - The default stays compatible:  dispose after a microtask when not re-attached.
     - `keepAlive: true` keeps the root across moves, with `onConnect` / `onDisconnect` hooks.
     - `onCleanup` works (dispose runs inside the root).
  7. An error boundary, on by default (`createErrorBoundary` around the render):
     - an `onError(element, err)` option
     - a `fallback(element, err)` option, which renders replacement content (see section 3a)
     - `:state(errored)` when internals exist
  8. Owner lookup crosses shadow roots (`getRootNode().host`), keeping rc.11's foreign-runtime guard.
  9. Adopts an existing declarative shadow root, instead of throwing (no hydration yet).
- Hiding Solid 2 traps where a default can:
  - the component runs untracked
  - props arrive already converted, so no per-prop memo layer is needed
- `UPSTREAM.md`:  one section per fix.
  - The upstream issue / PR it answers.
  - A proposed patch outline against `solidjs/solid` `next` `packages/element`
    (inlining the needed parts of `component-register`).
  - Nothing is filed upstream without Owen's go-ahead.
- Tests (vitest browser mode):
  - one file per fix, reproducing the original bug against `component-register` behaviour, and asserting the fix
  - plus the `@solidjs/element` README examples, as a compatibility suite

### 3. Port the Solid spike onto the fork

- `ElementDefinition.ts` shrinks to "vocabulary → prop definitions with `Converters`-based converters".
  Delete:
  - the capturing registry
  - `stashUpgradedProperties` / `restoreUpgradedProperties`
  - the removal `HACK`
  - the `reflecting` / `fromAttribute` flags
  - `convert()` / `reflect()`, `safeKey()`
  - `RegisterPropDefinition`
- `UIHost.ts` loses its `attachShadow` / `attachInternals` / stash code.
  - `FormHost` becomes fork options + hooks.
  - `UIElement.isolate()` goes (the fork's boundary replaces it).
  - `this.attrs.x` becomes the fork's converted props.
- `keepAlive: true` for all our elements:
  state survives moves, and `PartContext` stops relying on a re-render for reparenting.
- Record LOC before / after per file, in the report.

### 3a. Native fallback when a component fails (both spikes, exploratory)

- The fallback markup is LIBRARY-NEUTRAL, so both spikes render the identical thing.
  - `src/components/ui-<name>/ui-<name>.fallback.ts`:  a small class per component,
    building plain DOM from the host's attributes and light-DOM children.
  - `button`:  a native `<button>` (or `<a href>`) around a `<slot>`;  it still submits / resets the form.
    It carries `type`, `disabled`, `name`/`value`, `aria-*`, the class grammar and `part="button"`.
  - `dropdown`:  a native `<select>` (multiple when `multiple`), built from `options` / `<ui-item>`s.
    Its value is kept in sync with the host's form value.
  - `label`, `segment`, `container`, `divider`, parts:
    the root element with its class grammar, around a `<slot>` (no behaviour to lose).
  - `icon`:  the `label` text (or nothing), with the `aria-hidden` rules kept.
- Hooked in by the element base, on failure:
  - Solid:  the fork's `fallback(element, err)` option (the boundary's fallback)
  - Lit:  `UIElement` catches errors from `update()` / `render()`,
    renders the fallback into the shadow root once, and stops re-rendering that instance
  - both:
    - `:state(errored)`
    - one console error, with the tag and cause
    - a cancelable `ui-error` event, so an app can log or replace
- Styling:  the fallback markup uses the same class grammar, so the component's adopted sheet still styles it.
- Tests (identical in both spikes):  force a throw in render, then check:
  - the fallback is present
  - a sibling still updates
  - the fallback button's click submits its form
  - the fallback select changes the host's form value
  - axe passes
- Report:
  - bytes per component for fallback code
  - what degrades (keyboard patterns, search, labels)
  - a recommendation on whether to keep it

### 5. Icon loading exploration (drive-by)

- What's true today:
  - Icon data is NOT copied per icon or per component.
    - One `Icons` class cache per bundle.
    - ~20 chunks of ~200 icons each (solid, split by letter range);  `regular` and `brands` as single chunks.
  - The real waste is GRANULARITY:
    - Drawing one icon loads its whole chunk:  up to ~17 KB gzip for solid, 224 KB gzip for ANY brand logo.
    - Two separate bundles on one page each load their own copy.
- JS instead of JSON, by itself, changes nothing.
  - Vite already emits every `import("./x.json")` as a JS module chunk (`dist/solid-w-z-*.js`).
  - What matters is how many icons one request carries.
- Candidates, measured side by side in `spike/icons/` (a throwaway experiment, not wired into the spikes):
  1. today:  chunked data, JS chunks
  2. one ES module per icon (`icons/solid/user.js` → `[w, h, path]`)
     - The URL is computed from the name, so no name→loader index.
     - Apps can also import specific icons statically, and tree-shake.
  3. one SVG file per icon, copied from `@fortawesome/fontawesome-free@7` `svgs/{solid,regular,brands}/`
     (verify the v7 package ships them):
     - 3a. CSS `mask-image: url(…/user.svg)` on the icon box, with `background: currentColor`:
       zero JS, browser-cached, works in SSR output;  needs CORS when served cross-origin
     - 3b. `fetch` + inline `<svg>` (today's rendering, per-icon requests, in-memory cache)
- Measure for each:
  - bytes and requests to draw 1 / 10 / 50 distinct icons
  - time to first icon
  - disk size of the package
  - behaviour inside shadow roots
  - `currentColor` + dark mode
  - bundled-app use (offline)
  - duplicate bundles on one page
  - licence handling:  CC BY 4.0 attribution;  the SVGs carry a licence comment
- Keep regardless:  the lazy alias maps, `Icons.resolve()` names, the `ui-icon` markup contract.
- Output:  [the icons doc](icons.md) gets a "Loading strategies" section, with the table and a recommendation.
  - Switching `src/icons` over is a follow-up for Owen to approve, not part of this step.
