J1 Where the favicon's image data lives

The favicon's image data is kept as text inside a TypeScript file, not as image files next to the server. You'd only notice it when changing the icon: you regenerate that file instead of swapping a PNG.

  • Chose packages/server/src/site/favicon.ts: the SVG and both PNGs, as base64 strings.
  • The file is GENERATED by yarn favicon in packages/server (the script is scripts/favicon.ts); nobody edits it by hand.
  • Over: an assets folder, read from disk at run time.
  • Why: the VS Code extension bundles WebServer with esbuild. A file sitting beside the source code isn't there once the extension is installed.
  • The site header's bundles drop the PNG strings (tree-shaking: the bundler leaves out code nothing uses). The header only uses the SVG.

J2 How big the hat is in the favicon

The white hat fills 74% of the icon's width, the brand's own proportion, rather than being enlarged to read better at tiny sizes. You'd see it in a browser tab, where the icon is drawn at 16px.

  • The brand says "about three-quarters"; its CSS uses 72%.
  • Tried 82%. At 16px on a 1x (non-retina) screen the bigger hat gains about one pixel, and it reads as a hat silhouette either way.
  • At 16px on a retina screen (32 device pixels) and above, 74% is crisp, and the bigger hat crowds the corners.
  • One SVG serves every size, so it's one number for all of them.

Example: to try a bigger hat, run yarn favicon --hat 0.8 in packages/server. It rewrites the icon files and prints a summary line ending in hat 0.8.

The options:

  1. 74%, the brand's proportion (chosen).
  2. 82%, a bigger hat for small sizes: one pixel gained at 16px, crowded corners at larger sizes.

Net effect:

  • the tab icon keeps the brand's proportions at every size
  • changing it later is one flag: yarn favicon --hat 0.8

J4 Which servers answer favicon requests

Every local web server in the repo answers favicon requests, whether or not it does live reload. But only pages served with live reload get the icon's <link> tags added to them.

  • The /_server/favicon.* routes and /favicon.ico are on every SRV.WebServer:
    • the page server
    • spell serve
    • the app's API server
    • VS Code's doc preview
    • ui's StaticServer
  • The icon LINKS are injected only where live reload is, which means pages served by the page server.
  • /favicon.ico answers with the 32px PNG directly: no redirect, so one request.
  • Where /favicon.ico sits in the order a request is tried:
    • AFTER the static folders, so a folder with its own favicon.ico wins
    • BEFORE fallback, so a single-page app's catch-all doesn't answer the request with its own index.html
  • A page whose <head> links its own icon gets no injected links.

J39 How search results are ranked

Each result gets a score from how well it matches, weighted by what kind of result it is. The page you're on comes first and attributes last, and each group is ordered by its best hit.

How the whole query matches the result's title, or one of its terms (a term: its tag, an aka, a topic or a page name):

Match Title Term
exact 1000 700
at the start 800 500
at a word start 600 350
inside a word 400 200
  • Or, every word of the query at a word start somewhere: 300, plus 100 per word found in the title.
  • Times a weight per kind:
    • On this page: 1.25
    • Components and Pages: 1
    • other pages' Sections: 0.9
    • Attributes: 0.8

  • Examples:
    • vertical on the Divider page: On this page first, then Sections, then Attributes
    • or: Components first
