<Section title="Behaviour">
  A form control only belongs to a `<form>` in its own part of the page, so a custom element can't be the form itself.
  `<ui-form>` is the form's LOOK and its VALIDATION around a native `<form>` you write:  one inside it (preferred), or
  the one around it.  It never creates or moves one, so frameworks keep owning that markup.

  Submission stays native.  `<ui-input>`, `<ui-textarea>`, `<ui-checkbox>`, `<ui-radio>` and `<ui-dropdown>` submit their
  `name` / `value` in the form's `FormData` like native inputs;  `<ui-button type="submit">` and Enter in a `<ui-input>`
  submit, `form.reset()` puts every control back to its starting value, and `<fieldset disabled>` disables what is
  inside it.

  Validation runs on submit:  the `rules` property (Fomantic's `fields` shape, keyed by `name` or `id`) plus each
  control's own constraints (`required`, `type="email"` ...).  An invalid submit is stopped before the page's own
  submit handlers run:  the failing fields show a prompt inside their `<ui-field>`, the form goes into the `error`
  state (showing its error `<ui-message>`s), `ui-failure` fires and the first invalid field is focused.  A valid submit
  fires `ui-success`, which is cancelable:  `preventDefault()` stops the native submission, e.g. to send it with
  `fetch()` instead.  `on="blur"` or `on="change"` also validates each field as the user leaves or changes it, and a
  field showing a prompt always re-validates as it changes.

  <Example
    title="Validation"
    description="`rules` is set from script;  submit empty, or tab through the fields (`on` is `blur`).  `ui-success` is cancelled here, so the values show below instead of the page navigating."
    code={`<ui-form on="blur">
  <form>
    <ui-fields widths="2">
      <ui-field required>
        <label for="name">Name</label>
        <ui-input id="name" name="name" placeholder="Name"></ui-input>
      </ui-field>
      <ui-field required>
        <label for="email">E-mail</label>
        <ui-input id="email" name="email" type="email" placeholder="joe@schmoe.com"></ui-input>
      </ui-field>
    </ui-fields>
    <ui-field required>
      <label for="password">Password</label>
      <ui-input id="password" name="password" type="password"></ui-input>
    </ui-field>
    <ui-field>
      <ui-checkbox name="terms">I agree to the terms</ui-checkbox>
    </ui-field>
    <ui-button type="submit" primary>Sign up</ui-button>
  </form>
</ui-form>

<script type="module">
  const form = document.querySelector("ui-form")
  form.rules = {
    name: "notEmpty",
    email: ["notEmpty", "email"],
    password: ["notEmpty", "minLength[6]"],
    terms: "checked"
  }
  form.addEventListener("ui-success", (event) => {
    event.preventDefault() // no native submission
    console.log(event.detail.values)
  })
  form.addEventListener("ui-failure", (event) => console.log(event.detail.errors))
</script>`}
    open
  >
    <FormDemo />
  </Example>

  A field's rules are a rule name, a list of them, or an object with the list plus options.  Rule names are Fomantic's:
  `notEmpty`, `checked`, `email`, `url`, `integer`, `decimal`, `number`, `regExp[...]`, `is[...]`, `not[...]`,
  `contains[...]`, `minLength[n]`, `exactLength[n]`, `maxLength[n]`, `size[a..b]`, `match[field]`, `different[field]`,
  `creditCard`, `minCount[n]`, `exactCount[n]`, `maxCount[n]`, `range[a..b]`, `minValue[n]` and `maxValue[n]`.  A rule
  object's `prompt` replaces the default message, with the same placeholders (`{name}`, `{value}`, `{ruleValue}`).

```js
form.rules = {
  email: ["notEmpty", "email"],
  confirm: ["match[password]"],
  nickname: { rules: ["minLength[3]"], optional: true }, // skipped while blank
  company: { rules: ["notEmpty"], depends: "is-business" }, // skipped while that field is blank
  password: { rules: [{ type: "minLength[8]", prompt: "Use at least 8 characters" }] }
}

form.validate() // validate every field and show prompts;  true when valid
form.isValid() // the same verdict, showing nothing
form.values // { email: "...", confirm: "...", ... } by name
form.reset() // the native reset, and prompts cleared
form.clear() // every control emptied, and prompts cleared
```

  `ui-valid` and `ui-invalid` fire for each field as it is validated.  `error-focus="no"` keeps focus where it is after
  a failed submit, and `prevent-leaving` asks before the user leaves the page with changed values.  Without a native
  form, `<ui-form>` still validates (`validate()`, `on="blur"`), but nothing submits.

<Section title="Theming">
  Theme with the public `--ui-form-*` tokens:  set one on the element, on any ancestor (`:root` included), or on the
  form's box through `::part(form)`.  They inherit into the shadow root, where the sheet reads each through a private
  alias, so nothing inside blocks them;  the form hands them to its fields and rows, so set them on the form (a field
  outside a form reads them from its own ancestors).  `inverted` swaps in `--ui-form-inverted-label-color`.  The
  `--_ui-fields-*` tokens are private (a row hands them to its fields):  use `width` and `widths` instead.

```css
ui-form {
  --ui-form-gutter: 2em;
  --ui-form-label-font-weight: normal;
  --ui-form-required-color: var(--ui-primary);
}
```

<Section title="Accessibility">
  - The form is your native `<form>`, so submission, `FormData`, reset and the browser's form handling are unchanged.
    `<ui-form>` turns off the browser's own validation bubbles while it is connected (and restores them after), so
    its prompts are the only ones shown.
  - Label every control:  a `<label for>` pointing at the `ui-*` control's `id` names it, as the examples do.  In an
    inline row, give the controls without a visible label an `aria-label`.
  - Group radios and checkboxes in `<ui-fields grouped>` (or `inline`) with `role="radiogroup"` / `role="group"` and
    `aria-labelledby` pointing at the group's label.
  - `required` on a `<ui-field>` only draws the asterisk.  Put `required` on the control, or a `notEmpty` rule, so it
    is enforced.
  - A prompt is a `role="alert"` label inside the field, so it is announced when it appears;  failing controls get
    `aria-invalid="true"` until they pass.  After a failed submit focus moves to the first invalid field.
  - `loading` sets `aria-busy`;  `loading` and `disabled` make the form `inert`, and a `disabled` field is `inert`
    too, so their controls can't be reached.
  - Without JavaScript the native fallback keeps the same layout and the native form still submits, with the
    browser's own constraint validation taking over.  It drops `rules`, prompts, the `ui-valid` / `ui-invalid` /
    `ui-success` / `ui-failure` events, `values` and the methods, `prevent-leaving`, and the error state after a
    failed submit.
</Section>

<Section title="Framework usage">
  Keep the native `<form>` in your template, set `rules` as a property, and handle `ui-success` (cancel it to submit
  with `fetch()`).

```jsx
// React 19
<ui-form rules={rules} onui-success={(e) => { e.preventDefault(); save(e.detail.values) }}>
  <form>...</form>
</ui-form>
```

```html
<!-- Vue 3.5: compilerOptions.isCustomElement = (tag) => tag.startsWith("ui-") -->
<ui-form :rules="rules" @ui-success.prevent="(e) => save(e.detail.values)">
  <form>...</form>
</ui-form>
```

```jsx
// Solid 2:  no `on:` namespace, so listen from a ref callback
<ui-form
  prop:rules={rules}
  ref={(el) => el.addEventListener("ui-success", (e) => { e.preventDefault(); save(e.detail.values) })}
>
  <form>...</form>
</ui-form>
```

</Section>
