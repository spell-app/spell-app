Page Server

How the repo serves its pages locally: the $/server library (SRV), the one page server per checkout built on it, and everything that plugs into it.

Written for: anyone opening, editing or serving a page, or adding routes to the page server Status: built (P1-P7) Checked on: branch unified-server, 2026-10-02, against the code (not just the plan: epics/unified-server)
  • packages/server (@spell-app/server, $/server, SRV): serving pages locally, for every package.
    • Before it, six servers each had their own mime table, path check, port choice and opener; now they share one library.
  • The PAGE SERVER (yarn server): ONE per checkout -- the main one, and each worktree -- serving the whole repo on one port.
    • live reload on every page; edit a section in place; the server-only properties
    • / redirects to the docs index
    • port: 4747 if free (SPELL_SERVER_PORT overrides), else any free one; the real one is written to <root>/.spell-server.json, where the openers find it
    • its output goes to <root>/.spell-server.log
  • Every page carries <spell-site-header>: a fixed bar switching between the five PROPERTIES, with the checkout's worktree / branch badge, an "open in VS Code" link, edit mode and a light / dark toggle.

The page server itself, $/server/page: opt-in, since it brings parse5 and loads route modules.

  • PageServer.ts -- THE server: a live WebServer on the checkout, plus /_server/ping, the editor, /ui/ and the route modules.
    • PageServer.ensure(root): what yarn server ensure, goals and the openers call
  • PageEditor.ts -- /_server/page: read, replace or patch a page's source
  • RunningEpics.ts -- running epics' plan docs on the main checkout's server: /worktrees/<w>/, /_server/epics, and their cards in the docs index's Epics section (Running epics)
  • cli.ts -- yarn server
  • page.types.ts -- RouteModule, RouteContext, PageServerSettings

Browser code, $/server/site: bundled into the docs' spell-ui.js and Spell UI's site bundle (packages/ui/site/_assets/site.js).

  • SiteHeader.ts -- <spell-site-header>: own shadow DOM and CSS, no UI elements, so it looks the same on every property
  • SectionEditor.ts -- <spell-section-editor>: edit mode's hover, dialog and save
  • site.types.ts -- PROPERTIES, the header's list
  • index.ts -- defineSite(): defines the header, and mounts the editor on served pages
  • The barrel is node built-ins only: json5 and esbuild come in as the caller's hooks (parseJson, transforms).
  • Its users: ui's tools and site, spell/node, cli, app, docs, goals, the VS Code extension.
  • page/ may use dependencies (parse5); site/ is DOM code. Neither is in the barrel.

Each flow, step by step, in the order it happens.

  1. The opener (yarn docs:open, yarn plan-doc open, yarn goals open) calls PageServer.ensure() -- the docs' scripts through ensurePageServer().
  2. It reads the pid file, .spell-server.json, and asks that server's /_server/ping: it counts only if it answers for THIS checkout.
  3. None: it spawns cli.ts serve under tsx, detached, logging to .spell-server.log, and waits up to 15s.
    • about 1s when it has to start, 0.3s when it already runs
  4. The URL is base + the file's path from the checkout, shown in:
    • a Chrome tab keyed by the page's path, so the same page from another checkout reuses it
    • a new browser window (goals), or VS Code's Simple Browser
  5. Every .html page it serves gets window.SPELL_SERVER (port, token, file, ETag, branch) and /_server/live.js before </head>.
  1. fs.watch on the named folders only -- "pageServer".watch (packages/docs), plus goals/ from goals' route module -- never scripts/ or experiments/. The whole root would flood it (node_modules, .git, worktrees).
  2. Each changed path waits 250ms for quiet: a write is often two (write, then a formatter).
  3. A change event with the URL path goes to every page holding /_server/events open; a heartbeat every 30s keeps the streams alive.
  4. The page reloads if the path is its own file, or any .css / .js; its scroll position survives.
  1. The header's pencil turns edit mode on, for this tab.
  2. Hovering outlines the editable thing under the pointer: an element with an id (sections, paragraphs, list items, cards ...), or a section through its heading's id.
  3. "edit" fetches its source fresh: GET /_server/page?path=&id=[&parent=section] -> { html, etag }.
  4. Save sends PATCH /_server/page?path= with the token and If-Match.
  5. The server:
    • checks the token and origin, and that the path is an .html file inside the checkout
    • takes the file's FileLock; a changed ETag is a 409
    • finds exactly ONE #id with parse5 (none: 404, several: 409), and splices its byte range: every other byte stays as it was
    • writes a temp file and renames it over the original
  6. Live reload shows the result. Nothing is committed: the change waits in the working tree.
  • Also: PUT replaces the whole page; scripts in a page call SPELL_SERVER.editPage({ id, html }).

An epic's plan doc lives in its worktree until it merges, and each worktree has its own page server. The main checkout's server shows them all anyway:

  1. /worktrees/<w>/... serves worktree <w>'s files (a StaticHandler mount on .claude/worktrees; dot files still 403). A plan doc's relative assets resolve inside its own worktree.
  2. /_server/epics lists them, as JSON: each worktree's own epic (named like the worktree), and any epic the main checkout lacks. Copies of epics merged before the worktree was cut are skipped.
  3. The docs index's <!-- running-epics --> marker, first in its Epics card list (yarn docs:index puts it there), becomes the running epics' cards on each request: running and merged epics in one list, each title after its state (planning, 3/6, done, stalled), and a merged epic's card dropped when it runs in a worktree too. None running, or opened from disk: nothing.
  4. A worktree's plan doc changing reloads its page and the index (one recursive watch on .claude/worktrees).
  5. yarn server url and the VS Code preview hand out these URLs for a worktree's file (SRV.mainServerUrl()), so every link is on port 4747.
  6. yarn plan-doc doesn't rewrite the committed index inside a worktree: two worktrees doing so conflicted on merge. The epic's card comes with Doc Review's yarn docs:index.

The editor is the PAGE SERVER's child, so yarn server alone runs it too: the app's route module (appRoutes.ts) starts it with EditorServer once the page server listens (onListening), and stops it with the page server (onStop).

  1. --port, if given, goes to a page server this STARTS as SPELL_EDITOR_PORT (default 3000, else any free port); one already running keeps its editor where it is.
  2. PageServer.ensure(): the page server, with every route module. Once it listens, the app's module starts vite (its script, under this node, in packages/app) with PORT = the page server's port and API_SERVER=127.0.0.1, so its proxy sends /api there; its output goes to .spell-server.editor.log.
  3. Once vite answers, the module records it in .spell-server.editor.json: the page server's /editor redirects there.
  4. spell serve waits (up to 90s) for that record to answer; opens the editor, unless --headless.
  5. Ctrl-C: stop the page server -- and with it the editor -- only if spell serve started it.

How a package adds routes to the page server without the server importing it.

  • A ROUTE MODULE is a file whose default export is a RouteModule: { name, setup(context) }.
    • setup() runs once, before the server listens
    • loaded by dynamic import under tsx; a failure is logged, not fatal
  • RouteContext, what setup() gets:
    • router -- add routes; they run BEFORE static files
    • guard -- put guard.writeCheck on every route that changes something
    • live -- live.watch(dir) reloads pages when files under it change
    • web -- the whole server, e.g. web.files.html.push() for an html hook
    • root, info -- the checkout; pid, port, branch
    • onListening(start) -- run once the server listens (info.port is set), e.g. to start a child process that needs the page server's port: the app's editor
    • onStop(stop) -- run when the server stops, e.g. to end a child process
  • Listed in the repo root's package.json, "pageServer": routes (paths from the root) and watch (folders to live-reload, default packages/docs).

A route module: goalsRoutes.ts, abridged · 30 lines 
import { SRV } from "$/server"
import type { RouteModule } from "$/server/page"

const goalsRoutes: RouteModule = {
  name: "goals",
  setup({ router, guard, live, web }) {
    live.watch(GOALS, { ignore: /(^|\/)_(tools|skills)\// })
    web.files.html.push((html, { file }) =>
      file.startsWith(`${GOALS}/`)
        ? html.replace("</head>", `<script>window.GOALS_SERVER = ${JSON.stringify({ api: API })}</script>\n</head>`)
        : html
    )

    const api = new SRV.Router()
    api.get("/claude", (_request, reply) => reply.set("Cache-Control", "no-store").json(claude(true)))
    api.use(guard.writeCheck, SRV.parseBodies({ limit: MAX_BODY }))
    api.post("/thought", (request, reply) => {
      const body = request.body as { target?: string; text?: string }
      const target = resolveTarget(body.target ?? "", preferences())
      const id = addThought(target, String(body.text ?? "")) as string
      reply.json({ ok: true, id: id.toUpperCase(), target: target.name })
    })
    // ... /run, /claude/login, /open-vscode
    router.use(API, (request, reply, next) =>
      api.handle(request, reply, (error) => next(error === undefined ? undefined : goalsError(error)))
    )
  }
}

export default goalsRoutes
  • The page server parses no bodies itself; each route parses its own:
    • page edits: 10mb
    • goals: 64kb
    • the app's /api: JSON5, 10mb
  • Why: a proxy (/ui) must stream the raw body, and a body can be read only once.
  • A second parseBodies() in a chain leaves an already-read body alone, instead of waiting for a stream that has ended -- found when goals' buttons hung.

A local server is reachable by every web page the browser opens; these keep it to its own pages.

  • Loopback only: every server binds 127.0.0.1, so nothing on the network reaches it.
    • exception: the app's standalone API (yarn start:server) binds 0.0.0.0 with no host check, as Express did, for vite and LAN devices
  • Host check, on every request and websocket: 127.0.0.1:<port>, localhost:<port> or [::1]:<port>, else 403. A site pointing its own name at 127.0.0.1 (DNS rebinding) is refused.
  • Write token: random each run, given only to pages the server serves (window.SPELL_SERVER.token), sent as x-server-token.
    • a page from an older run must reload: "bad token: reload the page"
    • an Origin header, when sent, must be the server's own
  • resolveInside() is the ONE path check:
    • each segment decoded on its own: an encoded / (%2F) is a 400
    • .., . and NUL bytes refused
    • the result checked to be inside the root after resolving, as a last line
  • Dot files are 403 unless a mount says dotFiles: .git, .env and .spell-server.json stay private. Live reload never reports them.
  • Page edits: .html files inside the checkout only, never committed.
  • If-Match MUST be the ETag the page was served with (size + modified time): missing 428, stale 409. This catches writers that don't lock: VS Code, an agent's edit tool.
  • FileLock (<file>.lock, created atomically) makes cooperating tools take turns: page edits, yarn plan-doc, yarn goals, the app's saves.
    • waits up to 20s; a lock older than 60s is a crashed holder's, and taken over
  • The app's /api: no token -- the editor calls it from vite's origin, through vite's proxy -- but a write whose Origin isn't this machine is 403. Express had no check at all.

Known costs and open caveats, from the plan doc's Caveats.

  • Slower under tsx: goals.sh help 0.05s with node, 0.18s under tsx; yarn goals help ~0.6s, mostly yarn.
  • Less portable: goals now needs this repo's packages/server, tsx and the root "pageServer" field.
  • Already-open goals pages need one reload: the token header moved from x-goals-token to x-server-token.
  • A page opened through ?file= with no page server running gets the extension's own server: no goals buttons and no /ui/ until yarn server start.
  • "Open in VS Code" opens in the LAST FOCUSED VS Code window, not this session's.
  • The header's theme toggle and the Spell UI site's can disagree.
  • The editor has no site header, and the Editor tab leaves the page server's origin.
  • No edit mode on a worktree's page through the main server: PageEditor refuses dot paths too. The worktree's own server edits it.
  • A main server started before this code (an old checkout, not restarted) has no /worktrees/: mainServerUrl() checks /_server/epics first, and links fall back to the worktree's own server.
  • Phases are read by pattern (the server is a leaf: no HTML parser): a plan doc whose phase tags lose data-phase / data-status shows as "planning".
  • /ui/ shows the COMMITTED bundle: a library change shows only after yarn site:build in packages/ui.
  • _assets/icon-packs is a symlink into packages/ui/src/icons/: served fine, but a static deploy must copy through it.
