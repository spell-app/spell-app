Commands

Every operation the spell CLI, the Claude skills and the yarn scripts can do, side by side: which does it, under what name, and where it should live.

Written for: Owen and agents, about to add a CLI command, a skill or a yarn script (the root AGENTS.md sends them here first) Status: inventory + target moves not made yet Data: commands.json beside this page, drawn by the page server
  • Three ways to make the repo do something, grown apart:
    • spell CLI: 20 commands, mostly the spell language; two pass straight through to repo tools (spell plan-doc, spell goals)
    • yarn: 170 scripts in 14 package.json files; the same 8 copied into 10 packages
    • skills: 12 in the repo, 7 more in ~/.claude/skills that it uses (the goals ones are symlinks into goals/_skills)
  • Behind them, a fourth layer with no name: the tools that do the work (scripts/window.mjs, plan-doc.js, goals.js, five python scripts), and steps that live only in a skill's PROSE, redone by hand every run. The runs column shows which.
  • Target: the CLI drives everything; skills keep only judgement and dialog, yarn scripts become short aliases (5. Target, 6. Roadmap).
  • Rows are OPERATIONS, not commands: a gap shows as an empty cell, and one command can serve several rows.

How each one works, and how a new command is added to it.

  • packages/cli: commander, running every package's SOURCE through tsx (no build; ~0.5s to start)
  • yarn cli:install symlinks spell onto your PATH, pointing at ONE checkout; spell plan-doc / spell goals look upward for the nearest checkout instead, so they work in a worktree
  • Conventions: results on stdout, progress on stderr; --json on 7 commands; exit 0 ok, 1 errors, 2 bad command line
  • A new command: src/commands/<name>Command.ts, exporting (session, args, options) => Promise<exitCode>; add it to the barrel, an options type to cli.types.ts, and a block to main.ts:
packages/cli/src/main.ts · 7 lines 
program
  .command("projects")
  .description("list the project roots -- or, given one, the projects in it")
  .argument("[root]", "a project root, e.g. @library or @user")
  .option("--json", "print the list as JSON")
  .action((root: string | undefined, _options, command) =>
    run(CLI.projectsCommand, root ? [root] : [], command.optsWithGlobals())
  )
  • .claude/skills/<name>/SKILL.md: prose Claude follows, front matter saying when to use it; helpers in its scripts/
  • Also in play: ~/.claude/skills's goals* (symlinks into this repo's goals/_skills), session and worktrees (user-level python the repo's skills call)
  • Hooks (.claude/settings.json): WorktreeCreate / WorktreeRemove (.claude/hooks/worktree.mjs), Stop (.claude/hooks/handoff.mjs, moves a session between windows)
  • A skill is a WORKFLOW (/isolate, /park), not an operation: it keeps its short name, and should call one command per repo action

  • Names:
    • colon vs dash: docs:new beside plan-doc, vscode's install-extension
    • noun:verb vs verb:noun: docs:new, icons:pack beside start:server, build:runner, gen:icons
    • typecheck has three names: ts, tsc (solid-element), check (vscode; ui-site's check is astro's)
    • serve (root: every server), server (the page server), ui serve (smoke pages): three things
  • Wrong or misleading:
    • test:browsers installs browsers; fork:install is plain yarn install
    • ui lint:fix runs the fork's NON-fix lint; solid-element has no lint:fix, ts or review, so the root's skip it
    • copies drift: ; vs && after the echo (cli, spell), yarn tsc vs tsc (spell)
  • Pure wrappers: root docs:*, plan-doc, server; ui site:*, test:fork, fork:build
  • Never referenced: app start:server:prod, spell test:coverage / test:fixtures, cli spell
  • Runtimes differ: node, tsx, node --import tsx with TSX_TSCONFIG_PATH, node --experimental-strip-types
  • No release / publish / version script anywhere

Steps no script does: Claude redoes them by hand each run, and they drift between skills.

  • name collision check (/isolate, /epic)
  • carrying edits into a worktree: /isolate uses a bare git stash pop, which the shared-stash rule forbids
  • merge readiness (git merge-tree exit codes), merging main in, checks for the packages touched (/isolate, /park, /bedtime)
  • merging into main: /isolate says --ff-only, /whassup --no-edit
  • cleanup candidates: /isolate done parses worktrees.py's text, while whassup.py computes the same in code
  • PARKED and MORNING notes: templates, state headers, edits (/park, /wait-for, /bedtime, /wakeup)
  • a goals decision takes 3 commands (add decision, close, log); the topic's .md notes are synced by hand
  • modal plumbing everywhere: 4 options per question, "Recommended" first
  • reading Claude's session registry, "is it alive", its folder: 4 python scripts
  • a session's title: 3 times (status.py, handoff.mjs, session.py)
  • the main checkout from a worktree (git rev-parse --git-common-dir): 5 scripts
  • "is a question waiting": transcript.py and whassup.py
