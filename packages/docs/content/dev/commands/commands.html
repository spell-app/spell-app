How each one works, and how a new command is added to it.

  • packages/cli: commander, running every package's SOURCE through tsx (no build; ~0.5s to start)
  • yarn cli:install symlinks spell onto your PATH, pointing at ONE checkout; spell plan-doc / spell goals look upward for the nearest checkout instead, so they work in a worktree
  • Conventions: results on stdout, progress on stderr; --json on 7 commands; exit 0 ok, 1 errors, 2 bad command line
  • A new command: src/commands/<name>Command.ts, exporting (session, args, options) => Promise<exitCode>; add it to the barrel, an options type to cli.types.ts, and a block to main.ts:

  .description("list the project roots -- or, given one, the projects in it")

  • .claude/skills/<name>/SKILL.md: prose Claude follows, front matter saying when to use it; helpers in its scripts/
  • Also in play: ~/.claude/skills's goals* (symlinks into this repo's packages/docs/tools/goals/skills), and, until 2026-10-03, session and worktrees (now in .claude/skills, on spell dev)

Decided in epic commands (2026-10-02), with Owen; the plan doc has each one's details.

  • Doc, rule and roadmap first; moves later. Owen reviews the scheme before renames ripple through skills, docs and habit; each move is its own small epic.
  • Repo tools under spell dev. spell is headed for npm as the spell-language tool; a separate noun keeps repo tooling out of its way, over flat top-level commands or a second binary.
  • Noun then verb. Groups in help and tab-completion; the same words in CLI and yarn (server start / server:start).
  • Data in JSON, drawn by the page server. Owen's choice: plain JSON is easy to edit and to check, over a JS data file or tables written into the HTML. Cost: no file:// view (8. Limits).
  • Rows are operations, not commands. A gap shows as an empty cell; one command may serve several rows. Fine-grained: each subcommand and each copied script its own row.
  • A runs column. The roadmap is mostly about moving the tool behind a command into the CLI, so the tool is shown.
  • Drift check by hand. yarn commands:check is in no review: a new yarn script in one package shouldn't fail another's checks. The AGENTS rule says to run it.
  • One language: the python tools ported to TypeScript (2026-10-03, Owen). They live in packages/cli/src/dev/, node built-ins only, so a lean spell dev entry stays possible; each port was compared with the python on live data before it was deleted. doc-links.js is plain Node, not a Python imitation: same page edits, plainer messages.
  • session and worktrees moved into the repo. They were user-level skills, but tied to this repo all along; now they call spell dev like the rest.
  • Package scripts stay in yarn. Tool-native scripts already have a good home; wrapping them adds ~0.5s a call. spell dev check (R7) orchestrates them instead.
  • The check reads main.ts as text. From a worktree, the checkout checked may not be the one spell runs from.
  • The tables need the page server: from file:// the page shows a notice where they go (yarn docs:open dev/commands/commands.html).
  • The filter hides rows and empty families, not their entries in the contents column.
  • spell is linked to ONE checkout (yarn cli:install); spell dev commands find the nearest checkout themselves, but their CODE is the linked checkout's. In a worktree, node packages/cli/bin/spell.mjs runs its own.
  • The CLI takes ~0.6s to start (tsx compiles on each run), where the python took ~0.05s: it adds up in a skill that calls it often (/worktrees, /wtf), until R10.
  • Skills need spell on the PATH (yarn cli:install, once per machine), and it runs the LINKED checkout's code: a spell dev command added on a branch exists for skills only once merged.
  • spell dev session open was checked by reading, not run: running it opens a VS Code tab.
  • The marks are judgement: "could" vs "couldn't really" is an opinion, written down.
  • The check sees names, not meaning: it can't tell that a row's marks or target went stale.
