Design only, nothing built (P16). One element you put at the top of a page. It loads the components the page uses, takes the page's settings, sets theme and size for what is inside, and can hide the page until it is ready. Open decisions are questions Q13 to Q21, each with the options side by side.

A page using it (today the same page needs a script per family, an icon-set element, a stylesheet class):

         emoji="fomantic"
         lang="es"
         theme="dark" size="small"
         display="when-ready"

  <ui-card>       <!-- first one loads ui-card -->

  </ui-card>
</ui-root>

Loading on demand

  • The root watches its subtree (a MutationObserver plus a first scan for :not(:defined), the way site/src/scripts/components.ts does now). For each undefined ui-* tag it imports that tag's FAMILY once.
  • Tag => family today is GUESSED in familyOf() (plural, content parts => parts, EXTRA_TAGS) over an import.meta.glob. The coming roll-up src/components/component-definitions.ts (every tag => its folder, noun, topics, P14) replaces the guessing, and also gives the root skeletons (below).
  • Each family is its own package entry (@spell-app/ui/ui-card after the P13 rename). The root imports them with a dynamic import() per family, so a bundler (or an import map) makes one chunk each. Loading a family calls define(), which upgrades the waiting elements.
  • Open: where the root lives (Q18), what a family that never loads does (Q15).

  • Attributes as shorthand, with the <ui-*-set> children kept for options like prefix / only: Q20.
  • Nested roots: Q14.

Theme and size

  • Both are CSS that inherits, so the root sets them for its subtree with no JavaScript logic: theme="dark" adds the ui-dark class (color-scheme: dark; every colour token is a light-dark() pair, so it flips) and theme="light" ui-light; size="small" sets --ui-scale from the size ratios (medium sets --ui-scale: 1, which also resets a size from outside). Design: packages/ui/docs/theming.md.
  • Tokens: any --ui-* custom property in the root's style (or the page's #ui-app-stylesheet) reaches every component inside, through shadow roots, like the example's --ui-radius: 0. No new mechanism.
  • theme and size are subtree-only by nature, so settings differ in scope: CSS ones per subtree, icons / emoji / lang per page (Q13).

Display: hide until ready

display While components load Needs
immediately draws as it goes: unstyled, then upgrades nothing
when-ready subtree hidden (visibility: hidden, space kept) until every needed family is defined and its elements are ready the roll-up
skeleton subtree hidden, grey shapes drawn in each element's place until ready the roll-up + skeleton descriptions
  • "Ready": every element has a ready promise (host.markReady() in UIElement, once content has rendered with its styles; loaded() is the runtime-and-sheets part), and a :state(ready). The root waits for the families (the imports), then for the ready of each element it saw, and then sets its own state ready and dispatches ui-ready.
  • The hiding is a CSS rule on the root's own shadow (::slotted(*)) or the page sheet, and lifts by removing one state: no per-element work.
  • Defaults and traps: default value (Q19), a family that never loads (Q15), server-rendered HTML (Q16).

Skeleton description

  • A skeleton is made of the shapes ui-placeholder already draws (header, paragraph, line, image). A component declares what its skeleton looks like as plain data; the root draws it as a stylesheet (CSS gradients, in em so size still scales it), not as extra elements. An undefined tag can be styled from a page stylesheet, so this works before the family loads.
  • Open: where the description lives so the root can read it before the family loads (Q21), and how it sizes to content it hasn't seen (Q17).

Q10 Table: opt in to stacking by own width with a TOKEN (--ui-table-stack-by: container), or an attribute (stack-by="container")?

Tables stack by viewport again (Fomantic). The layout agent chose a token; a container stackable class would clash with .ui.container.

Q11 WebKit: style-query rules on ::before / ::after go stale after a token change (breadcrumb divider icon, feed number circles): nudge the element after the change, or move those rules off style queries?

See I7. 3 WebKit tests fail on it (breadcrumb x2, feed x1). A WebKit bug: the element's own style updates, its pseudo-element doesn't; any inline style write refreshes it. The breadcrumb case is real (its glyph loads async).

Q12 WebKit: <ui-form> can't stack rows on a narrow form, because WebKit's container lookup doesn't cross the slot: give the form a real box host, or another mechanism?

See I8. 1 WebKit test fails. The host is display: contents, so it can't be the container; the container is .ui.form inside the shadow root.

Q13 Root: are page settings page-wide or per subtree? (icon packs, emoji names, lang)

Plain words. An icon pack or emoji name set is a page-wide thing today: UI.icons and EmojiData are ONE per page, so two <ui-icon-set>s add up. A <ui-root> in the middle of a page could set them for just its own subtree (a docs demo that wants Lucide icons beside a page that uses Font Awesome), but every icon would then have to find its nearest root.

The problem case: two roots on one page disagree.

<ui-root icons="fa7-free">...</ui-root>
<ui-root icons="fomantic">
  <ui-icon name="home"></ui-icon>
  <!-- which pack? -->
</ui-root>

theme, size and tokens are CSS and inherit, so they are per-subtree for free. Only icons, emoji and lang are in question. (lang chooses a dictionary, which renames TAGS, and customElements is one registry per document: tags cannot be per-subtree.)

A. Page-wide (recommended)

Settings apply to the whole page, merged in order, like <ui-icon-set> today. A second root with a conflicting emoji or lang logs a warning (last wins). Cheapest: no change to UI.icons. 

icons="fa7-free fomantic"
<!-- adds to UI.icons -->
B. Per subtree

Each icon asks its nearest root for packs. Needs a lookup through shadow roots on every icon, and a cache per root. Isolated demos, but dictionaries still can't be per-subtree. 

<ui-root icons="lucide">
  <ui-icon name="home">
<!-- nearest root's packs -->
C. Split

Icons / emoji / lang page-wide, theme / size / tokens per subtree (they inherit anyway). In code the same as A: this is A, said out loud in the docs.

Recommend A: one runtime per page, so one set of page settings. Revisit B only if a docs page needs two icon sets side by side.

Q14 Root: nested roots, does an inner root override or merge?

Plain words. A <ui-root> inside another <ui-root> happens (a widget that ships its own root, dropped into a page that has one). What does the inner one do? 

<ui-root theme="dark" icons="fa7-free">
  <ui-root size="small"
           display="immediately">
    <ui-card>...</ui-card>
  </ui-root>
</ui-root>

Questions in that example: does the inner root stay dark? Does it wait for its own families or the outer one's? Does the outer display hide it?

A. Inner inherits, adds (recommended)

Theme / size / tokens inherit by CSS (inner overrides only what it sets). Page settings merge (see the scope question). Loading: the inner root reports to the OUTER one, which is ready only when every inner root is. The outer display hides everything under it; an inner display matters only once the outer is ready.

B. Inner is inert

A root inside a root does nothing but warn. Simple, but a self-contained widget breaks the moment a page also has a root.

C. Independent

Each hides and loads its own subtree. The outer is ready when ITS descendants (not the inner root's) are. Can flash: the outer shows while the inner is still hidden.

Recommend A: matches how CSS inheritance already works, and gives one "everything is ready" answer for the page.

Q15 Root: when-ready timeout and error policy (a family that never loads)

Plain words. display="when-ready" hides everything until every family is loaded. If one import fails (offline, 404) or a tag has no family at all, the page would stay blank forever. We need a rule for how long to wait and what to do. 

<ui-root display="when-ready"
         timeout="3s">
  <ui-card>...</ui-card>
  <ui-cardd>typo</ui-cardd>
</ui-root>

Two kinds of failure: a tag with NO family (ui-cardd: the roll-up has no entry, known at once) and a family whose import REJECTS or hangs. The docs site's loader today logs a rejection and carries on (Promise.allSettled in site/src/scripts/components.ts).

A. Reveal after a timeout (recommended)

Unknown tags are ignored (one console.warn). A rejected import is logged and counts as settled. After timeout (default 5s) the root reveals anyway and fires a cancelable ui-error per failure. A broken family never blanks the page; its elements show their native fallback.

B. Stay hidden

No timeout. Strict: never shows half-built UI. But one offline chunk blanks the page, which the native fallback (docs/fallback.md) exists to avoid.

C. Reveal on first error

Wait with no timeout, but reveal the moment any import rejects. A hang (never settles) still blanks the page.

Recommend A, plus a ui-ready event (detail: { failed: [...] }) so an app can react.

Q16 Root: server-side rendering and Declarative Shadow DOM

Plain words. Server-side rendering (SSR) means the server sends finished HTML. ui-* elements can arrive with their shadow root already in the HTML (Declarative Shadow DOM, DSD: <template shadowrootmode="open">), so they paint before any JavaScript runs. test/dsd.test.ts already covers a button. A root that hides everything until JS is ready would throw that away. 

<ui-root display="when-ready">
  <ui-button>
    <template
      shadowrootmode="open">...</template>
    Save
  </ui-button>
</ui-root>

An element's ready state is set only after the runtime runs, so in server HTML every element looks "not ready" and the root cannot know the families are present.

A. Hide only with JS (recommended)

Hiding is a CSS rule inside @media (scripting: enabled): server HTML shows as sent, and with JS on, when-ready hides what is not yet upgraded. The media query works in all current engines. 

@media (scripting: enabled) {
  ui-root[display=when-ready]
    :not(:state(ready)) { ... }
}
B. Always hide

Simple, but with JS off or slow the page is blank: server rendering gains nothing under a root.

C. SSR out of scope

Matches T4 (SSR hydration is later work): when-ready is JS only, documented. Cheapest, but locks a behaviour in.

Recommend A: one media query, and DSD pages don't regress.

Q17 Root: how does a skeleton size to content it has not seen?

Plain words. A skeleton is a grey stand-in sized like what will replace it, so the page doesn't jump when real content arrives ("layout shift"). But before a family loads, nobody knows how big a <ui-card> will be: its real size depends on its own content (a title, an image, three lines). 

<ui-root display="skeleton">
  <ui-card>
    <ui-header>Report</ui-header>
    <ui-description>
      3 lines of text
    </ui-description>
  </ui-card>
</ui-root>

What the skeleton can see: the TAG (ui-card), its ATTRIBUTES (size="small", fluid), its child TAGS. It cannot see the real text height until fonts and styles are in. A skeleton description (3.5) gives a default size per tag, in em, so size still scales it.

A. Default size per tag (recommended)

Fixed width / height in em from the description, plus the attributes it understands (fluid => width fill). Slotted children ignored. Some shift is accepted; authors pin with style="min-height: 12em".

B. Mirror the children

Walk the real children and draw a shape for each part (ui-header => a bar, ui-description => lines). Closer, but needs every part's description, and text length is still a guess.

C. Authors give a hint

A skeleton attribute: <ui-card skeleton="3 lines, image">. Exact when written, but nobody will write it.

Recommend A for v1; B can reuse the child tags' own descriptions later.

Q18 Root: does <ui-root> live in core or in its own entry?

Plain words. "Entries" are the files you import: @spell-app/ui/core (used by EVERY family), @spell-app/ui/ui-card (one family) ... The root is the first thing a page loads, so it must be small. In core it ships in every family bundle, even on pages that never use a root; core is meant to stay small. 

import "@spell-app/ui/ui-root"
// the tiny loader, or
import "@spell-app/ui/core"
// root included

The root needs the roll-up (component-definitions.ts, tag => folder, a few kB for ~60 families), an import() per family, a MutationObserver and the skeleton sheet. It does NOT need the runtime (UI.load()) until the first family loads.

A. Its own entry (recommended)

@spell-app/ui/ui-root, src/components/ui-root/ like any family. Imports core only for UIElement. Pages that don't use it pay nothing. It must NOT import the families statically.

B. In core

Every family carries it, nothing extra to import. But core grows by the whole tag table for every page, even ones that import their families by hand.

C. Not an element

A function, UI.root({ ... }), plus a thin tag. Smallest, but loses the plain-HTML story.

Recommend A: matches "one folder per family". The loader piece (the roll-up reader) can also be a runtime service so site/src/scripts/components.ts reuses it.

Q19 Root: default display, when-ready or skeleton?

Plain words. display says what the page shows while components still load. immediately: draw as you go (unstyled boxes, then they pop in). when-ready: nothing until everything is in. skeleton: grey stand-ins until everything is in. What should a plain <ui-root> do? 

<ui-root>...</ui-root>
<!-- default? -->
<ui-root display="skeleton">...</ui-root>
A. when-ready (recommended)

Nothing draws until ready. No flash, no shift after reveal; blank for a moment on a slow connection. Needs no per-tag descriptions, so it works for every tag from day one. Skeleton is opt-in as families gain descriptions.

B. skeleton

Best feel, but only as good as the descriptions: a tag with none must fall back to when-ready anyway, so the default behaves differently per tag.

C. immediately

Zero blocking, but undefined tags show as plain text, then jump: the flash a root exists to prevent.

Recommend A: predictable, and Owen's own example ("nothing draws until the components are set up"). Skeleton is the upgrade.

Q20 Root: page settings as attributes, as child elements, or both?

Plain words. Today a page adds an icon pack with a child element <ui-icon-set src> and picks emoji names with <ui-emoji-set names>. A root could take the same as attributes. Attributes are short; elements carry more options (prefix, only, base for icon packs). 

<ui-root icons="fa7-free fomantic"
         emoji="fomantic"
         lang="es"
         assets="/assets/ui/">

<!-- today -->
<ui-icon-set src="fa7-free">
<ui-emoji-set names="fomantic">

Mapping: icons => UI.icons.use(id) per word (built-in ids), emoji => EmojiData.use(), lang => the dictionary (docs/translation.md, not built yet), assets => base for pack.js and emoji chunks (BuiltInPacks.base).

A. Attributes AND elements (recommended)

Attributes cover the common case (built-in ids, one set). Anything with options (custom src, prefix, only, base) stays a child <ui-icon-set> inside the root. Both reach the same UI.icons: the attributes are shorthand, no new behaviour.

B. Attributes only

One way to write it. icons would need a mini-syntax for prefix / only / base, and <ui-icon-set> would be retired: a breaking change.

C. Elements only

The root takes no settings, only loads and themes. No change, but loses the one-tag page setup.

Recommend A. assets should be ONE url for packs and emoji chunks (assets/icon-packs/, assets/emoji/), so a host copies one folder.

Q21 Root: where do skeleton descriptions live?

Plain words. Owen: "component files can export a skeleton description". The catch: the skeleton shows BEFORE the family's file is loaded, so it can't be read from the class. Reading it from the class would mean loading the family first, which is the wait the skeleton hides. 

// ui-card.skeleton.ts
export const cardSkeleton = {
  width: "18em", lines: 3
}
// UICard.tsx reuses it
@proto static skeleton =
  cardSkeleton
A. Static on the class

Simplest to write. Only available after the family loads, so the root could use it only mid-load. Defeats the main use.

B. Separate small file (recommended)
