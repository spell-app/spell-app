Rulex

Rulex is the regex-like syntax that writes $/parser rules: "give {thing:expression} (to {recipient})?". This page is its reference: every construct, what it compiles to, how the result matches, the traps, and how markdown would be written in it.

Written for: anyone writing parser rules, spell's or a new language's (the markdown epic first) Status: reference of rulex as built Researched on: branch markdown, 2026-10-03. Every syntax and match below was run through the real rulex parser (Sources)
  • A syntax string is compiled ONCE, when the rule is registered, into a tree of ordinary rule objects (Sequence, Choice, Repeat, Keyword ...). Parsing never sees the string again.
  • Seven constructs: keywords, symbols (\ escapes any), {subrule}, (a|b), [item delimiter], numbers and name: labels. Three modifiers: ?, +, *; counts ({1,6}), /i. Spell uses all but numbers, in 133 registrations.
  • Every rulex special character escapes with \: \? \* \+ \( \) \[ \] \{ \} \| \: \\. Nothing else needs escaping.
  • TWO tokenizers are involved, and only one is the language's. The rules MATCH the language's tokens (spell's, or a markdown tokenizer's). But rulex READS each syntax string with its own: RulexTokenizer, words, numbers, symbols and whitespace only (since 2026-10-04). So --, //, #, quotes and <tag> are ordinary symbols in a syntax; before, spell's tokenizer turned them into comments, text and JSX (6. Traps).
  • What the rules it builds match: token VALUES, exact and case-sensitive, SPACED AS WRITTEN (since 2026-10-04): parts written touching must touch (\*\*{x}\*\* refuses * *x* *), spaced ones may space, and {space} / {spaces} require one space / some. Counts as regex: #{1,6} takes 1 to 6 and stops. /i matches any case.
  • With a markdown tokenizer for the input and the planned rulex changes, every markdown line kind (headings, breaks, fences, lists, tasks, tables, quotes, alerts, links, images) is one short syntax: #{1,6}{spaces}{text}, (-|\*|\+){spaces}{text}, !\[{alt}\]\({url}\).
  • Not rulex: code spans ("any token up to the matching backtick run") and emphasis' delimiter rules. Those are rules built in code. 7. Markdown has every case.
  • Code: packages/parser/src/rulex/. rulex.ts defines rulex's own grammar, built in code from plain P.Symbol / P.Word / P.Sequence rules (rulex can't define itself). RulexParser.ts holds the helpers.
  • Opt-in: import "$/parser/rulex" registers it as P.Parser.rulexParser. The P barrel never pulls it in. Without it, a rule with syntax throws "Rulex parser is not installed".
  • Rulex is itself a P.Parser (RulexParser), whose default rule is sequence. That's why its own rules have tests in the same [input, output] form as spell's.
  1. parser.addRule(Class, { syntax, tests }) calls Class.instantiate(), which constructs the rule.
  2. The Rule constructor: given syntax but none of rules / rule / literal / literals, it calls initFromSyntax(syntax).
  3. Rule.compileSyntax() runs rulexParser.compile(syntax): tokenize, parse as rulex's sequence, compile to a rule tree.
  4. The tree's props are copied onto the instance (explicit props win), then it's frozen.
  • Eager, not lazy: a bad syntax fails at registration (import time for spell's modules), not at parse time. No cache: each registration compiles afresh.
  • A Sequence class whose syntax compiles to a single non-sequence rule wraps it: rules: [compiled]. Any other mismatch throws "Syntax '…' compiles to a X, which Y does not extend".
  • Several ways to write one rule: register the class again with another syntax. The instances merge into a P.Group under the rule's name. No array form.
  • syntax, tests and ruleName are NOT inherited; share a syntax through a const (spell's VARIABLE_SYNTAX).
  • Rules built while parsing (spell's methods and enums) compile syntax the same way, from strings they assemble: (expression:red|green|blue).
packages/spell/src/rules/math.ts · a rule with syntax and tests 
class plus extends InfixOperatorSuffix {
  @proto static precedence = 13
  @proto static parenthesize = true
  getOutputOperator() {
    return "+"
  }
}
math.addRule(plus, {
  syntax: "(operator:plus|+) {expression:simple_expression}",
  tests: [
    {
      compileAs: "expression",
      beforeEach(scope: P.Scope) {
        scope.variables?.add("price")
        scope.variables?.add("tax")
      },
      tests: [
        ["price + tax", "(price + tax)"],
        ["price+tax", "(price + tax)"],
        ["price plus tax", "(price + tax)"]
      ]
    }
  ]
})

Construct Syntax Compiles to Notes
number 1 Keyword(1) Matches a number token of that value. Unused in spell. Digits only: 1.1 is 1 . 1, -1 is - 1. (Before 2026-10-04 both were ONE number, and 1.1.1 crashed the compile.)
keyword give Keyword("give") One word token. Words may hold - and _ after the first letter
keywords aa bb cc Keywords(["aa","bb","cc"]) A run of keywords merges into one rule
symbol : Symbol(":") Any one punctuation character
symbols >= Symbols([">","="]) A run of symbols merges, spaces in the syntax or not
escaped symbol \? \( \| Symbol("?") Any symbol, including the special ones. As literals, | ) ( [ { MUST be escaped: bare, they close or open a choice / list / subrule
subrule {expression} Subrule(expression) Another rule, looked up by name at parse time (so it can be recursive)
named subrule {thing:expression} Subrule(thing:expression) The match lands in match.groups.thing. {thing: expression} works too
choice (>|a) Choice[Symbol(">") Keyword("a")] Nests: (is|(negated:is not|isn't))
choice of literals (a|an) Keyword(["a","an"]) All-keyword or all-symbol choices merge into one literal rule
named choice (op:+|-) Symbol(op:["+","-"]) Spell names 45 choices, operator: most (27)
sequence give {thing} (to {who})? Sequence[…] The whole syntax. A sequence of one rule is just that rule
list [{item},] Repeat(Subrule(item) / Symbol(",")) Item, then delimiter; either may be any rule: [({a}|{b})(,|or|and)]. A trailing delimiter is allowed. Only ? may follow ]
named list [list:{expression},]? Repeat?(list:…) The name goes INSIDE the bracket

Written straight after a construct (or, for spacing, between them), changing how it matches.

Modifier Syntax Compiles to Notes
optional the? {x}? (…)? Keyword("the")? Sets optional on the rule
one or more word+ Repeat(Keyword("word")) Wraps in a Repeat
zero or more {sub}* Repeat?(Subrule(sub)) An optional Repeat
exactly n x{7} Repeat(Keyword("x")), minCount = maxCount = 7 Regex's interval, straight after any rule. { + digit is a count; { + letter stays a subrule
n to m #{1,6} Repeat(Symbol("#")), 1..6 Repeat already has minCount / maxCount; rulex just sets them
n or more -{3,} Repeat(Symbol("-")), 3.. x+ ~== x{1,}, x* ~== x{0,}
case-insensitive (note|tip)/i, note/i Keyword(["note","tip"]), case-insensitive Regex's /i, after a keyword or a choice of literals. {x}/i is an error
spacing as written !\[{alt}\]\({url}\) vs {a} and {b} a part written touching the one before gets spacing: "none"; spaced, none (free) Touching in the syntax = touching in the input; a space in the syntax allows (not requires) one. A list's delimiter too: [{x},] wants x, y, [{x} ,] also takes x , y
symbol run #+ vs - + Repeat(Symbol("#")), itemSpacing: "none" A SYMBOL touching its flag repeats as a run, like **: #+ takes ##, not # #. Spaced before the flag, copies may space: - + takes - - - too. Other repeats (subrules, groups, keywords) space freely
one space \[{space}\] next part gets spacing: "one" Exactly one space between the parts either side: [ ], not [] or [  ]. Not a rule: zero-width, it owns that boundary
some spaces -{spaces}{text} next part gets spacing: "some" One or more spaces / tabs: - item, not -item. Must sit between two parts, unnamed and unflagged, or rulex throws
  • Runs of plain keywords merge into Keywords, and runs of plain symbols into Symbols.
  • An optional literal inside a run stays in it as { literal, optional: true }: a? b c is one Keywords.
  • (a|b|c) becomes ONE Keyword(["a","b","c"]), not a Choice.
  • A choice or sequence holding a single rule collapses to that rule. The choice's flags then win over the rule's own.
  • A plain nested sequence flattens into its parent.
  • A NAMED rule (name:) is never merged, since a merged rule can't carry one item's name.
  • tests: RuleTestBlock[]: each block is { title?, compileAs?, skip?, beforeEach?(scope), tests }, where tests holds [input, expectedOutput] pairs (arrays join with \n).
  • unitTestModuleRules(parser, module) ($/parser/test) runs every testable rule of a module, one describe per registration, titled with its syntax. It also snapshots each rule's group spec, so the Groups type argument can be copied from __snapshots__.

Rulex only builds rules. What they match is up to the rule classes and the LANGUAGE's tokenizer, not rulex's.

Rule Input Matches? Why
hello world Hello world no Exact, case-sensitive value compare (token.matchesLiteral())
hello world hello   world yes A space in the syntax allows any spacing; inline whitespace rides on the token before it
hello world hello⏎world no Newlines stay in the tokens
\*\*{word}\*\* * *hello* * no Written touching, so must touch (before 2026-10-04: yes, spacing was invisible)
\[{word}\]\({word}\) [ hello ] ( world ) no Same
{word} ' s hello's and hello 's both Written spaced, so may space, or not
-{spaces}{word} - hello / -hello yes / no {spaces}: one or more spaces required
[{word},] hello, world, yes A trailing delimiter is fine
[{word},] hello world 1 of 2 tokens Rules match at the HEAD of the tokens. Checking the rest was used up is the caller's job
  • A literal rule compares token values, whatever the token type: Keyword("a") would match a symbol token a. Keyword vs Symbol only changes how a rule prints back to syntax.
  • Choice parses EVERY alternative, then keeps the best by precedence, then length, then order. It is not a PEG-style first-match.
  • Sequence.test() checks that the sequence's own keywords and symbols appear in the tokens before parsing any subrule. That makes a miss cheap.

Two tokenizers, two kinds of trap:

  • Input side: the rules match whatever the LANGUAGE's tokenizer makes. Spell's turns --- into a comment; a markdown tokenizer, with no comment, quote or JSX rules, won't. Each language picks its own, so nothing to fix in rulex.
  • Syntax side: until 2026-10-04 rulex read every syntax string with the DEFAULT P.Tokenizer, which knows spell's comments, quotes and JSX: the column "Before" below. Now it has its own plain RulexTokenizer (words, numbers, symbols, whitespace), and every trap but **{text}** (rulex's own syntax) is gone. No spell syntax used any of those characters, so spell didn't notice.
Syntax Before Workaround then Now
# {text} heading comment: throws "Can't parse input" \# {text} (a # mid-syntax is fine) # is a symbol
a -- b comment: silently Keyword("a") a \-\- b two - symbols
a \-- b \, then a comment: silently a \ escape EACH dash escaped -, then -
--- comment: throws \-\-\- three - symbols
a // b comment: silently Keyword("a") a \/\/ b two / symbols
a "b c" d text token: silently Keyword("a") a \"b c\" d " is a symbol
'{x}' text token: throws \'{x}\'; one bare ' is fine (isn't) ' is a symbol
<b> {text} </b> JSX element: throws < {x} > (< not followed by a letter) < is a symbol
¬ / ∆ rewritten to newline / tab (a test-fixture convenience): throws none plain symbols
1. {item} Keyword(1) Symbol(".") same: numbers stay, for intervals
**{text}** the 2nd * of each pair is a repeat flag \*\*{text}\*\* same: * is rulex syntax, escape it
  • Before, rulex.compile() never checked that it used every token: it threw only when NOTHING parsed, else returned the rule built so far and dropped the rest.
  • Now it throws, naming what it couldn't read: (a|b gives "rulex couldn't read |b in (a|b". No spell syntax relied on the drop.
  • And an unescaped [, { or ( only ever OPENS a list, subrule or choice. Before, one that didn't close quietly became a literal symbol ([{sub}] compiled to literal brackets); now it throws. A literal one is \[, \{, \(.
  • rule.toRulexSyntax() prints a rule back as syntax. That's used for LSP descriptions and for spell's SPELL: DECLARES comments.
  • It keeps escapes and spacing (2026-10-04): \[{text}\]\({url}\), -- vs - -, -{spaces}{text}, [{item},] vs [{item} ,] all print back unchanged.
  • All 472 of spell's registered syntaxes print back exactly. What a rule doesn't keep can't print back: redundant parens ((of {x}?)) and a space inside a subrule ({value: expression}) come back without them, the same rule (spell's 5 such syntaxes were tidied). What rulex still can't say, after the plan:

  1. "As long as the opening fence": a count that depends on an earlier match.
  2. "Any token except X": a TokenType / Pattern rule with a blacklist, written in code, used as a {subrule}.
  3. Block structure (what nests in what, lazy continuation lines) and emphasis pairing: hand-written, by design (the markdown plan's "Parser vs hand-written").
