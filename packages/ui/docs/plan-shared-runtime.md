# Plan: shared-runtime packaging for both spikes + a forked Solid element layer

(The approved master plan now lives in `docs/plan.md`; this file is the plan for this step only.)

> NOTE (2026-10-09):  `@spell-app/solid-element`, the forked element layer this plan made ("the fork" below), is gone:
> epic `spell-element` folded it into `src/elements/`.

## Context

- Owen will build the spell app on Solid 2.  If `@spell-app/ui` components share the app's copy of Solid, the Solid runtime costs nothing extra per page, and app signals / context can flow straight into components.
- Today neither spike shares anything:
  - every build bundles its base library (Lit 7.5 KB, Solid 28 KB gzip) and our element core into each measured widget
  - smoke pages import `src/` through the dev server, never `dist/`
  - so every family carries a ~15 KB (Lit) / ~43 KB (Solid) "floor"
- Goal 1, both spikes:  the base library becomes a peer dependency, externalized;  our element core becomes ONE shared chunk;  each widget's cost is just its own classes + CSS + vocabulary.
- Goal 2, Solid only:  replace `@solidjs/element` + `component-register` with our own fork that fixes the gotchas the spike works around, written so each fix could become an upstream PR.
- Goal 3, both spikes:  when a component fails, fall back to a NATIVE element with equivalent function (a failed `ui-button` becomes a working `<button>`), so a page degrades instead of losing controls.
- Goal 4:  the two REPORTs become directly comparable -- same sections, same measurements, same table headers, numbers generated by the same scripts.
- Outcome:  both REPORTs and `docs/spike-lit-vs-solid.md` get a "shared runtime" section with apples-to-apples numbers, and the Solid spike's element core shrinks by deleting its workarounds.

## What the exploration found

- Build / measure (both spikes):
  - no `external`, no `peerDependencies`;  Solid groups `solid-runtime` into its own chunk only to count it
  - Lit's `measure.ts` builds in memory and buckets modules by id (already has an "own" measure);  Solid's `demo/measure.ts` regex-parses `dist/` and has no "own" measure -- the two aren't comparable
  - smoke pages load `/src/index.ts` or `$spike/index` from the dev server;  `duplicate-lit.html` and the Solid 1.9 host page test two runtimes
- Solid element layer (`node_modules/@solidjs/element` 84 lines + `component-register` 287 lines, both MIT, Ryan Carniato):
  - every spike workaround traces to a line:  bare booleans parse false (`component-register.js:60`), `true` reflects `"true"` (:69-71), pre-upgrade props dropped (:122), `removeAttribute` ignored on bare booleans (:161), per-instance accessors shadow `style`/`hidden` (:41), microtask reflection guard (:70/73), teardown on reconnect (:146-155), no `BaseElement`/registry/shadow options in `customElement()` (element :77-83), owner lookup stops at shadow roots (element :19-31)
  - upstream `component-register` has matching open issues (#15 formAssociated, #20 removed-attribute default, #5 reconnect, #38 `id`, #40 underscores) and unreviewed PRs (#30, #39)
  - NOT fixable by a fork (Solid 2 itself):  eager memos, no signal writes in owned scopes, two-arg `createEffect` -- a fork can only hide some of them behind defaults

## Approach

### 1. Shared-runtime packaging (both spikes)

- `package.json` in each spike:
  - base library moves to `peerDependencies` (+ `devDependencies` for tests):  `lit`;  `solid-js`, `@solidjs/web`, and the fork (below)
  - `exports`:  `./core` (shared element core), `./<component>` per family, `./index`
  - `sideEffects`:  component entries + CSS
- Vite library config (`spike/lit/vite.config.ts`, `spike/solid/vite.config.ts` + `vite.shared.ts`):
  - `rolldownOptions.external` as a function:  `/^lit(\/|$)|^lit-(html|element)(\/|$)|^@lit\//` for Lit;  `/^solid-js(\/|$)|^@solidjs\//` + the fork for Solid (subpath imports included)
  - a new `core` lib entry exporting the spike element core AND the foundation it uses (`$/ui/elements`, `$/ui/vocabulary`, `$/ui/util`, the `$/ui/runtime` loader, `Icons`), so component entries import it instead of inlining it
  - keep the `UIRuntime` chunk and icon data as lazy dynamic chunks (unchanged)
- One shared measurer, `spike/shared/SpikeMeasure.ts` (class), used by both spikes' `measure` scripts so numbers are comparable:
  - in-memory `vite build` (Lit's approach), bucket modules by id:  `library` (external -- measured separately by bundling the peer set once), `core`, `runtime (lazy)`, `icons (lazy)`, and per family `own` = classes + `ui-<name>.css` + vocabulary
  - min + gzip level 9 with esbuild, same for both
  - reports:  library, core, own per family, "page with one button" (library + core + button), "all eight" (library + core + Σ own), and "app already ships the library" (core + Σ own)
  - writes `measure-results.json` per spike
- Import-map smoke pages, SHARED by both spikes (`spike/shared/frameworks/`), so both run the identical checks:
  - `yarn build` then serve the spike's `dist/` + a vendored copy of its peer set (a tiny `vendor` build of the `lit` / `solid-js` subpaths used) so pages run offline and deterministically
  - one page per host (`vanilla`, `react`, `vue`, `solid`) + the existing `check.js` round trip;  the smoke runner writes the spike-specific `<script type="importmap">` (mapping `lit` / `solid-js` / `@solidjs/web` / `@spell-app/ui/…` to that spike's files) into each page;  React and Vue still come from esm.sh
  - Solid 2.0 everywhere:  the `solid` host page is a small Solid 2 app (`spike/shared/frameworks/solid/app.tsx`) compiled once with the Solid 2 plugin, with `solid-js` / `@solidjs/web` external, used for BOTH spikes
    - on the Solid spike it additionally proves:  one `solid-js` module instance shared by app and components (assert a module-level identity), app context reaches a component (owner adoption), an app signal drives a component prop with no glue, `ui-change` updates the app signal
    - on the Lit spike it is the plain "Solid 2 app consuming custom elements" check
  - Compatibility checks, clearly labelled as such in page title and report:  `compat-solid-1.9.html` (older Solid host alongside our Solid 2 copy) and `compat-duplicate-lit.html` (a second Lit copy loaded by full URL);  nothing else uses Solid 1.x

### 2. Forked Solid element layer:  `spike/solid-element/` (`@spell-app/solid-element`)

- New self-contained TypeScript package (MIT, header crediting `@solidjs/element` / `component-register`), linked into `spike/solid` with `"@spell-app/solid-element": "link:../solid-element"`
- API is a SUPERSET of `@solidjs/element` (same `customElement(tag, props, Component)`, `withSolid`, `noShadowDOM`, `getCurrentElement`) so it could replace it upstream;  additions go in an optional 4th `options` argument
- Fixes, each isolated in its own module + test so it maps to one upstream PR:
  1. Options:  `{ BaseElement, registry, shadowRootInit: { mode, delegatesFocus } | false, formAssociated, internals }`;  the package defines the class itself (no capturing-registry trick)
  2. Accessors on the PROTOTYPE, the standard upgrade step (own properties captured in the constructor, re-applied through setters), `"key" in el` true before connect, and a dev error for keys that shadow `HTMLElement.prototype` members unless renamed via `property`
  3. Per-prop `{ attribute, type, converter: { fromAttribute, toAttribute }, reflect }`;  default boolean rule:  present / `""` → true, removed → false, `true` reflects as `""`;  JSON parsing only for `type: Object | Array`
  4. `attributeChangedCallback` always applies removals;  change callbacks receive the source (`"attribute" | "property"`);  reflection is synchronous with a re-entrancy guard (no microtask window)
  5. `ElementInternals`:  `element.internals`, and `onFormReset / onFormDisabled / onFormStateRestore / onFormAssociated` hooks registered during setup
  6. Lifecycle:  default stays compatible (dispose after a microtask when not re-attached);  `keepAlive: true` keeps the root across moves, with `onConnect` / `onDisconnect` hooks;  `onCleanup` works (dispose runs inside the root)
  7. Error boundary on by default (`createErrorBoundary` around the render), `onError(element, err)` and `fallback(element, err)` options (the latter renders replacement content -- see section 3a), `:state(errored)` when internals exist
  8. Owner lookup crosses shadow roots (`getRootNode().host`), keeping rc.11's foreign-runtime guard
  9. Adopts an existing declarative shadow root instead of throwing (no hydration yet)
- Hiding Solid 2 traps where a default can:  the component runs untracked;  props arrive already converted, so no per-prop memo layer is needed
- `UPSTREAM.md`:  one section per fix with the upstream issue/PR it answers and a proposed patch outline against `solidjs/solid` `next` `packages/element` (inlining the needed parts of `component-register`).  Nothing is filed upstream without Owen's go-ahead.
- Tests (vitest browser mode):  one file per fix, reproducing the original bug against `component-register` behaviour and asserting the fix;  plus the `@solidjs/element` README examples as a compatibility suite

### 3. Port the Solid spike onto the fork

- `ElementDefinition.ts` shrinks to "vocabulary → prop definitions with `Converters`-based converters";  delete:  capturing registry, `stashUpgradedProperties` / `restoreUpgradedProperties`, the removal `HACK`, `reflecting` / `fromAttribute` flags, `convert()` / `reflect()`, `safeKey()`, `RegisterPropDefinition`
- `UIHost.ts` loses `attachShadow` / `attachInternals` / stash code;  `FormHost` becomes fork options + hooks;  `UIElement.isolate()` goes (fork boundary);  `this.attrs.x` becomes the fork's converted props
- `keepAlive: true` for all our elements (state survives moves;  `PartContext` stops relying on re-render for reparenting)
- Record LOC before / after per file in the report

### 3a. Native fallback when a component fails (both spikes, exploratory)

- The fallback markup is LIBRARY-NEUTRAL, so both spikes render the identical thing:  `src/components/ui-<name>/ui-<name>.fallback.ts`, a small class per component that builds plain DOM from the host's attributes and light-DOM children
  - `button`:  a native `<button>` (or `<a href>`) carrying `type`, `disabled`, `name`/`value`, `aria-*`, the class grammar and `part="button"`, around a `<slot>`;  still submits / resets the form
  - `dropdown`:  a native `<select>` (multiple when `multiple`) built from `options` / `<ui-item>`s, value kept in sync with the host's form value
  - `label`, `segment`, `container`, `divider`, parts:  the root element with its class grammar around a `<slot>` (no behaviour to lose)
  - `icon`:  the `label` text (or nothing) with `aria-hidden` rules kept
- Hooked in by the element base on failure:
  - Solid:  the fork's `fallback(element, err)` option (boundary fallback)
  - Lit:  `UIElement` catches errors from `update()` / `render()`, renders the fallback into the shadow root once, and stops re-rendering that instance
  - both:  `:state(errored)`, one console error with the tag and cause, a cancelable `ui-error` event so an app can log or replace
- Styling:  fallback markup uses the same class grammar, so the component's adopted sheet still styles it
- Tests (identical in both spikes):  force a throw in render → the fallback is present, a sibling still updates, the fallback button click submits its form, the fallback select changes the host's form value, axe passes
- Report:  bytes per component for fallback code, what degrades (keyboard patterns, search, labels), and a recommendation on whether to keep it

### 4. Reports -- one shape for both

- Both reports are REWRITTEN to one template, `spike/shared/REPORT.template.md`:  identical section order and headings, identical table headers, identical units (min + gzip level 9, kB = 1000 bytes), identical perf method
  - sections:  Setup & versions · Bundle (shared-runtime three-tier table) · LOC · Ergonomics · Performance · Framework hosts · Forms & a11y · SSR / DSD · Error handling & native fallback · Translation · Testing · Risks · Foundation bugs
  - numeric tables are GENERATED:  `spike/shared/ReportTables.ts` reads each spike's `measure-results.json`, `smoke-results.json`, `perf-results.json` and LOC counts and writes the tables between `<!-- generated:… -->` markers, so the two reports can't drift in format
  - prose from the existing reports is kept where still true, moved under the matching heading;  history (Milestone 0, Batch 1) goes to an appendix
- Shared perf harness, `spike/shared/PerfRun.ts`:  same 1000 options, same keystroke sequence, same metrics (update, + layout, next frame; min / avg / max; first open), with one per-library adapter for "wait until the DOM is updated" (`updateComplete` vs `flush()`)
- `docs/spike-lit-vs-solid.md`:  rewritten around the generated tables, three scenarios (plain page, app already ships the library, all eight), replacing floor-based numbers

### 5. Icon loading exploration (drive-by)

- What's true today:
  - icon data is NOT copied per icon or per component:  one `Icons` class cache per bundle, ~20 chunks of ~200 icons each (solid split by letter range), `regular` and `brands` as single chunks
  - the real waste is GRANULARITY:  drawing one icon loads its whole chunk (up to ~17 KB gzip for solid, 224 KB gzip for ANY brand logo);  and two separate bundles on one page each load their own copy
- JS instead of JSON by itself changes nothing:  Vite already emits every `import("./x.json")` as a JS module chunk (`dist/solid-w-z-*.js`).  What matters is how many icons one request carries.
- Candidates, measured side by side in `spike/icons/` (a throwaway experiment, not wired into the spikes):
  1. today:  chunked data, JS chunks
  2. one ES module per icon (`icons/solid/user.js` → `[w, h, path]`):  URL computed from the name, so no name→loader index;  apps can also import specific icons statically and tree-shake
  3. one SVG file per icon, copied from `@fortawesome/fontawesome-free@7` `svgs/{solid,regular,brands}/` (verify the v7 package ships them):
     - 3a. CSS `mask-image: url(…/user.svg)` on the icon box with `background: currentColor` -- zero JS, browser-cached, works in SSR output;  needs CORS when served cross-origin
     - 3b. `fetch` + inline `<svg>` (today's rendering, per-icon requests, in-memory cache)
- Measure for each:  bytes and requests to draw 1 / 10 / 50 distinct icons, time to first icon, disk size of the package, behaviour inside shadow roots, `currentColor` + dark mode, bundled-app use (offline), duplicate bundles on one page, licence handling (CC BY 4.0 attribution;  the SVGs carry a licence comment)
- Keep regardless:  the lazy alias maps, `Icons.resolve()` names, the `ui-icon` markup contract
- Output:  `docs/icons.md` gets a "Loading strategies" section with the table and a recommendation;  switching `src/icons` over is a follow-up for Owen to approve, not part of this step
