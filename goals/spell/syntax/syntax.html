The language

Goals for spell's syntax, the caveats, and what's likely to bite us.

Status: draft · first pass, not yet talked through Updated: 2026-10-01 Notes for agents: syntax.md

1. Summary
  • Spell reads as plain English, compiles to JavaScript, and learns new words: defining to turn (a card) over teaches the parser that phrase.
  • It works end to end: Solitaire (445 lines) runs, with types, aliases, events, animations and tests.
  • The weak spots are precedence and types: the examples are tuned to awkward syntax to dodge them.
  • The main language work for three months: the precedence and types plan (designed; 14 decisions open).

2. Today

Card.spell (excerpt) · 9 lines 
a card is a thing
cards have a suit as one of clubs, diamonds, hearts or spades
a card has a direction as either up or down
the color of a card is red if its suit is either diamonds or hearts otherwise it is black
a card "is face up" if its direction is up

to turn (a card) over:
	if its direction is up: turn it face down
	otherwise: turn it face up
  • How it's built: about 190 rules in TypeScript (packages/spell/src/rules/), on a general rule-based parser (packages/parser) whose rule syntax reads like regular expressions for words.
  • Spells grow the language: methods, quoted phrases and enumerations become new syntax, recorded in the compiled JavaScript so other projects can import them.
  • What's missing: while/until loops, text with values inside, dates, money, maps; alert / ask / confirm compile but don't run; nothing saves or loads data.
  • What bites today (CODE-DEBT.md):
    • phrases ending in an expression swallow what follows: the number of cards in the deck is 52 compiles to itemCountOf(deck == 52)
    • is a accepts any word; methods with the same wording on different types collide
    • parameters need parentheses; types are recorded but never used by the parser
  • Size: about 1,300 lines of real spell; about 1,400 tests.

3. Goals

Now → December 2026
  1. G1 Precedence that just works plan phases 0-1: a Pratt-style expression loop, bounded backtracking
  2. G2 Types the parser reads plan phases 2-3: typed signatures, no parentheses on parameters
  3. G3 Examples that read naturally no workaround parentheses, no get-it dances
  4. G4 The missing basics while/until, text with values in it, dates, and alert/ask/confirm that run
  5. G5 A phrase book every phrase spell understands, generated from the rules and their tests; see docs

  2. G10 Libraries that teach new words see thingverse

5. Questions
  1. Q1 Settle the 14 precedence and types decisions a few short sessionsdetails

    Context: packages/docs/precedence/precedence.html lists them. The most debated: a|an <known type> in a signature is a parameter; postfix operators stop binding tightest; TypeScript only advises.

    Suggestion: one dialog per group of decisions, here or in a /epic session.

  2. Q2 How many ways to say one thing? the talk says many; the editor could still suggest onedetails

    Suggestion: accept many, show one: the editor's completions and the phrase book use the most natural form, and a "tidy" command could rewrite others to it.

  3. Q3 Indentation and colons tabs plus optional colons today: keep?
  4. Q4 How should spells draw? JSX today; <ui-*> tags after Solid; or something more English?details

    Options: JSX with <ui-*> tags (programmer-friendly); English layout phrases ("a button labelled Deal"); drag-and-drop that writes one of these. See app.

  5. Q5 HyperCard's objects in the language? stacks, cards, fields, buttons as built-in things — or keep it generaldetails

    Today "card" in the examples means a playing card. A built-in card would collide.
  6. Q6 When do we promise not to break spells? 0.x churn now; a promise at 1.0?details

    site-structure.md (2020) proposed semver, six months of overlap, and upgrade scripts.

6. Risks
  1. R1 Ambiguity grows with vocabulary every new phrase can collide with an old one
  2. R2 Speed on bigger programs every alternative is parsed, nothing memoized; Solitaire takes about 100 ms warm
  3. R3 Unhelpful errors a line that doesn't parse becomes a comment; beginners need more help
  4. R4 Syntax churn breaks the docs write the reference after precedence lands, or generate it
