Precedence And Types

Why spell's grammar needs binding power and datatypes, what breaks today, and what to build.

  • Written for: Owen, and any agent about to change the parser's rules
  • Status: a draft to argue with. Nothing here is built.
  • Researched on: branch ts-conversion, 2026-09-30. Every "today" output was produced by running the parser, see Sources and experiments.

1. Summary
  • The parser can't say what an expression is (its type) or how tightly it binds (its precedence), so every rule guesses from shape.
  • All four language goals trace back to that one gap: paren-free signatures, of in method names, multi-word properties, real precedence.
  • Proposal: plumb two facts through every match, bindingPower and datatype.
    • Expressions parse by precedence climbing with bounded operands, plus a cheap bounded backtrack.
    • Members, signatures and call sites become lookups over types.
  • Two ideas from review are folded in: exclusive lists as a property of a list type, and a TypeScript backend the editor compiles a second time.
  • Types are named in spell's words everywhere, never JavaScript's.

2. The problems

Eight of them, each with what the parser does today.

Greedy operands, no backtracking
  • A rule whose syntax ends in {expression} gives that slot the rest of the line, operators included.
  • Choice returns exactly one candidate and Sequence accepts it or fails. The candidate that would have worked is never built.

  • Values in use: 0 (most rules), 1, 2, 3, 5, 6, 9, 10, 11, 12, 13, 14, 20, 100. No table says what any of them mean.

  • Nothing checks what the arguments are.
  • A project's own rules merge ahead of the built-ins, so they win ties.

Type facts written, never read
  • A datatype exists on ScopeVariable, on a type's properties, on about 12 rules and on a few AST nodes. Nothing on the parse or compile path reads any of them.
  • getNestedScopeForMatch() in methods.ts builds argument variables from names only, so (a card) and (x as text) lose their types.
  • Assignment, get, loops and where declare untyped variables.
  • A list type doesn't record its item type.
  • Methods exist only as parser rules. TypeScope.methods is never filled.
  • Built-in types are bare names. text and number aren't types in scope at all.
  • The only member lookup that walks super-types is in the language server, SpellLanguageService.propertyOf().

3. Parsing today
  • expression is a group of 42 rules, tried in module order. Rules added while parsing go first.
  • The only "term, then operators" rule is compound_expression: {lhs:simple_expression} {rhsChain:expression_suffix}+, precedence 12.
    • It runs a shunting-yard over the suffixes' precedences when it builds its AST.
  • simple_expression is not a narrower tier. It is "every expression rule except the left-recursive ones" (SpellParser.getNamesForRule()), so it still holds every prefix rule ending in {expression}.
  • Choice.parse() parses every alternative, then keeps one. Sequence.parse() takes each child's single match.
  • Normal parsing has no memo. compound_expression re-parses the alternatives the outer expression choice parses anyway, at every nesting level.

4. Binding power

Split the one number in two, and let operands stop where their owner says.

Two numbers, two jobs
precedence, kept bindingPower, new
Answers Of several rules matching the same tokens, which wins? How tightly does this operator or prefix rule hold its operands?
Read by Choice.getBestMatch(), order unchanged the expression loop and {operand} slots
Set on a handful of statements and atoms, from one documented table every suffix rule and every prefix expression rule
Typical use create_type beats assignment; a user's is red beats is_equal * before + before is before and before or

The expression loop
  • expression becomes ONE rule: a generic P.OperatorExpression, registered by spell over two groups.
    • term: today's atoms. Literals, variables, the X of, list rules, a new card, calls.
    • expression_suffix: today's infix and postfix rules, same classes.
  • compound_expression and the shunting-yard are deleted.
  • InfixOperatorSuffix.compileAST() keeps its API, so no suffix rule's output changes.
  • simple_expression is renamed term and means what it says. isLeftRecursive goes away.
TypeScript · 23 lines 
/** `expression`:  a term, then every suffix that binds tighter than `minBP`. */
class expression extends P.OperatorExpression {
  @proto static atoms = "term"
  @proto static suffixes = "expression_suffix"

  parse(scope: P.Scope, tokens: P.Token[], minBP = P.Operand.currentBP): P.Match | undefined {
    let lhs = scope.getRuleOrDie(this.atoms).parse(scope, tokens)
    if (!lhs) return undefined
    const suffixes = scope.getRuleOrDie(this.suffixes)
    for (;;) {
      const rest = tokens.slice(lhs.length)
      // only suffix rules with `bindingPower > minBP` may match here
      const suffix = P.Operand.boundedBy(minBP, () => suffixes.parse(scope, rest))
      if (!suffix) return lhs
      // one match;  its AST is `suffix.rule.compileAST(lhs.AST, rhs.AST)`, exactly as today
      lhs = this.combine(lhs, suffix)
    }
  }
}

// an infix suffix's syntax:  `(operator:and) {expression:operand}`
//   its rhs parses with `minBP = 6`, its own `bindingPower`, so `x and y is 1` is `x and (y is 1)`
//   and `a and b and c` is `(a and b) and c`:  left-associative, because the test is strictly greater
  • Rulex gets {x:operand}: "an expression bounded by MY bindingPower". {expression} still means a full one.
  • The bound is a module-level value, set and restored by Sequence.parse(): the same trick as allowRunOut in Sequence.ts, two assignments on the hot path.
  • Completion keeps working: the loop records expectations as Choice and Repeat do, and the memo key includes the bound.
  • Each position is parsed once per bound, so this does less work than today's double parse.

Bounded backtracking
  • Choice.parse() already computes every candidate. With more than one, it keeps them on the winner, best first.
  • When a later child of a Sequence fails, the sequence resumes from the previous child's next candidate.
  • No re-parsing. At most one retry per candidate. Nothing allocated when there is one candidate, the common case.

6. A datatype on every match

Binding power fixes shape. The type problems need the parser to know what an expression is.

The rule
  • It is the rule the codebase already follows for scopeVar: look it up WHILE PARSING, stash it on the match, never touch scope from getAST().
  • Rule.getDatatype(match), memoized as match.datatype. Default: the rule's existing datatype static.
  • No type yet is undefined, and is compatible with everything. Nothing that parses today stops parsing.

Sources
  • literals, from their rule
  • a known variable, from its scope record
  • a new card, a new list of cards
  • the X of Y and its X, from the member found on Y's type
  • a method call, from its return type
  • comparisons, aliases, and / or / not: choice
  • arithmetic: number, or text when a side is text
  • list rules: the item type, the list's type, or number

Sinks
  • method arguments: (a card), (x as text), with … as …
  • this and it inside a method, from its owner
  • new variables from set, get and X is Y
  • for each card in the deck and where, from the list's item type
  • on card-click with a card
  • a pile is a list of cards records the item type on Pile

Member tables
  • TypeScope.getMember(words) walks the super-type chain. The code moves from the language server, which then delegates.
  • Methods get real records, P.ScopeMethod: words, output name, parameters with types, return type, where declared.
  • These are the facts SPELL: DECLARES already writes, so an imported project rebuilds them.

Built-in types
  • thing, list, app, text, number, choice, date become real types in the root scope.
  • Members come from one data table per type: words, datatype, parameters, how it compiles.
  • So the same words mean different things on different types: the length of the name is .length, the length of the deck goes through the list helper.
  • Adding a built-in type is one table entry plus its runtime class. The Type Explorer's pack is generated from the same table.

Type vocabulary
  • Today one idea has several spellings: the AST says "string", rules say text; a list literal's rule says "array"; choice maps to boolean in one table while as yes or no compiles to 'choice'.
  • The runtime already speaks spell: spellCore.typeOf() turns string into text, boolean into choice, array into list.
  • The parser uses exactly that vocabulary wherever a type is stored: scope records, declarations, AST.
  • JavaScript's words are accepted only where a user WRITES them.

7. Signatures, calls and members

Paren-free signatures
  • a or an before a KNOWN type is a typed parameter: to add a card to a pile is to add (a card) to (a pile). The indefinite article means "any one of these".
  • to make a mess stays a phrase: mess is no type.
  • the before anything is literal words: to reset the stock pile. The definite article means "the one we all know".
  • Parens stay for what needs them: untyped (message), defaults, (with …).
  • to create a card becomes Card.create(), not create_a_card(). One existing test pins the old reading.

Typed call rules
  • A generated call rule carries its parameter types and its return type.
  • An argument whose type is KNOWN and NOT assignable to the parameter's rejects the rule. Unknown never rejects.
  • put the chip on the pot picks Chip's rule.
  • add the card to the deck falls past a user's add (a card) to (a pile) to the built-in.
  • The language server reads parameters from the method record. Today it regexes parens out of the method's name, in four places.

Multi-word members
  • A member_words rule matches one to N words that aren't structural: of the a an is has have in to and or if where. N is the longest member name known in scope.
  • Declarations use it for the name: the short rank of a card is:, a card has short rank as text, its short rank.
  • Declared words bypass the identifier blacklist, so short is fine. short-rank keeps working.
  • On a read, the words resolve against the type of what follows of.
    • Resolved: a known_property_expression, higher precedence. A declared last card beats the built-in ordinal rule.
    • A single unknown word stays permissive, as today: Deck.spell reads an undeclared is-set-up.
  • Class members such as card suits go through the same lookup. That replaces the per-property EnumerationRule, and fixes the suits of the card and dashed type names.

8. Exclusive lists

From review: make "an item lives in one list of this kind at a time" a property of the list TYPE.

The note. "Since we have our own List type, what if we had an exclusive list concept which says an item can only be in one object of my type at once, and does the add-removes-from-previous-parent that we do manually with pile? This should work for subclasses too, and deck would need to be a different descendant path so a card can be part of a deck AND part of one of the piles."

Declaration
  • Words to bikeshed: a pile is an exclusive list of cards.
  • Records exclusive on Pile.
  • Every subtype inherits the FAMILY rooted at Pile: tableau, foundation, stock-pile, discard-pile.
  • a deck is a list of cards is another family, or none. So a card can be in the deck and in one pile.

Derived member
  • The item type gains a read-only member named after the family root: the pile of a card.
  • It is the pile holding the card, or nothing.
  • It is declared on Card by Pile's line, so go-to-definition lands there.
  • It is written into SPELL: DECLARES, so an importing project rebuilds it.
  • This is what the type plumbing is for: one line adds a fact to TWO types.

Runtime
  • List.add(), addAtPosition(), removeItem() and clear() consult the list's family.
  • One WeakMap per family maps an item to its owner.
  • Adding removes the item from the previous owner of the same family first.
  • The derived member reads the map, reactively.
  • Scratch results from map() and filter() must NOT take ownership: one more reason for the debt item that makes them plain lists.
  • Pile.spell's to move and its bookkeeping go away. add the card to the pile does it.

Open questions
  • Is "in a deck and in a pile" the default, or must a shared family be said out loud?
  • May remove the card from the pile leave a card ownerless? Probably yes: a card on the table.
  • What happens to a copy of the pile: a plain list, or a second owner?

9. A TypeScript backend

From review: have the compiler emit TypeScript, and compile it a second time. The second step is a service the EDITOR has; a runner only ever loads the optimized JavaScript.

The idea
  • The spell compiler writes TypeScript: types from each match's datatype, standard decorators, JSX as JSX.
  • A second step checks it, then lowers it to the JavaScript programs run on.
  • That step is assumed available wherever spell is COMPILED: the app's editor, <spell-editor>, the language server. It may be expensive and in memory.
  • It is never in a runner: the app's run pane, VS Code's runner and <spell-app> load plain JavaScript, as today.
  • Three payoffs:
    • a second opinion on every line the parser wrote
    • type answers the parser doesn't have
    • compiled spell written the way hand-written spellCore classes are

The pipeline

 parse Per keystroke, synchronous, as today. Matches carry binding power and datatypes. Spell's own diagnostics show at once. emit After the 2 second pause. One .tsx per spell file, plus which AST node wrote each range of it. check Editor only, in a worker. Type errors, mapped back to spell ranges and spell's words. lower Editor only. Types stripped, decorators lowered, JSX compiled for Solid. save Project.compiled.js, and the .tsx beside it for editors that import the project. run Any runner. Plain ES modules from a blob: URL, importing only @spell/….

import { spellCore, Thing, Show, thing, prop } from "@spell/core"
import type { Pile } from "./Pile"

const RANKS = ["ace", 2, 3, 4, 5, 6, 7, 8, 9, 10, "jack", "queen", "king"] as const

/** a card is a thing */
@thing
export class Card extends Thing {
  /** card ranks */
  static Ranks = RANKS
  @prop({ oneOf: RANKS }) accessor rank!: (typeof RANKS)[number]

  /** card direction:  up or down */
  @prop({ oneOf: ["up", "down"] }) accessor direction!: "up" | "down"

  /** never declared in spell:  its type comes from `set the pile of the card to the pile` */
  @prop() accessor pile: Pile | undefined

  // … suit, color, is_face_down, short_suit:  as in Card.spell

  /** the short rank of a card is: … */
  get short_rank(): string {
    if (this.rank === undefined) return "?"
    if (typeof this.rank === "number") return "" + this.rank
    return spellCore.upperCase(spellCore.getItemOf(this.rank, 1))
  }

  /** to move a card to a pile */
  async move_to_$pile(pile: Pile): Promise<void> {
    if (spellCore.isDefined(this.pile)) spellCore.remove(this.pile, this)
    this.pile = pile
    spellCore.append(pile, this)
    await spellCore.pauseFor(50, "msec")
  }

  /** to draw a card */
  draw() {
    const classes = () => ["Card", "face-" + this.direction, this.rank, this.suit, "ui button compact fluid"]
    const click = (event: Event) => spellCore.RUNTIME.trigger("card-click", { card: this })
    const back = (
      <div class={classes()} onClick={click}>
        <i class="fitted bicycle icon" />
      </div>
    )
    return (
      <Show when={!this.is_face_down} fallback={back}>
        <div class={[...classes(), this.color]} onClick={click}>
          {this.short_rank + " "}
          <span class="suit">{this.short_suit}</span>
        </div>
      </Show>
    )
  }
}
  • Parameter and return types come from the datatypes of section 6.
  • A property is @prop … accessor, the spelling spellCore's own classes use, not a hand-lowered accessor pair.
  • pile was never declared in spell. The emitter declares it from its first assignment.
    • It also becomes reactive, which an ad-hoc property is not today.
  • JSX stays JSX. className is class.
  • The early return became a <Show>: a Solid component runs once, so a branch must be an expression.
  • Each class needs a private brand. TypeScript is structural, spell's types are nominal: without one, a deck and a pile with the same members are the same type.

How it guides the compile
  • The parser never waits for TypeScript. Parsing is synchronous and per keystroke; checking is asynchronous, after the pause. So its answers arrive one compile late.
  • Inferred types, fed back:
    • the return type of a method or getter, and the type of an undeclared property
    • recorded on the scope record after a clean check; the next parse reads them like any declared type
    • this REPLACES the parser's own return-type inference: less code in the parser
    • saved in SPELL: DECLARES, so a project imported without its sources has them too
  • A better candidate, offered:
    • where a choice kept several candidates and the winner fails the check while another passes
    • shown as a quick fix, "did you mean put (a chip) on (a pot)", never applied silently
  • Hover and completion can ask typeAt() wherever spell's own datatype is unknown.
  • Fed-back types can change a later parse, through typed call rules.
  • So every host that compiles runs the same check, and a cold compile repeats emit and check until the types settle: twice at most.
  • The parser's own choice is never overridden. TypeScript reports, suggests, and fills in types.

Errors back in spell's words
  • Half of the mapping exists: every AST node keeps the match it came from, file and offsets, even a member hoisted into another file's class.
  • The other half is missing: compile() joins strings and forgets where each came from.

/** Emitted text, plus which AST node wrote each range of it. */
type Emitted = { text: string; spans: EmittedSpan[] }
type EmittedSpan = { start: number; end: number; node: P.ASTNode }

class ASTInfixExpression extends ASTExpression {
  // today:  a string, and where it came from is lost
  compile(): string {
    return `${this.lhs.compile()} ${this.operator} ${this.rhs.compile()}`
  }

  // proposed:  the same one-liner;  the tag asks each node for its own `emit()`, shifts its spans
  // by where it landed, and adds one span for `this`
  emit(): Emitted {
    return P.emit(this)`${this.lhs} ${this.operator} ${this.rhs}`
  }
}

/** Innermost node whose output covers `offset`:  its `match` is a range in a spell file. */
function nodeAt(emitted: Emitted, offset: number): P.ASTNode | undefined {
  let found: EmittedSpan | undefined
  for (const span of emitted.spans) {
    if (span.start > offset || span.end <= offset) continue
    if (!found || span.end - span.start <= found.end - found.start) found = span
  }
  return found?.node
}
  • The helpers in stringifyAST.ts that re-indent shift spans as they go. The project header's length is added once.
  • The same spans are a source map: stack traces and breakpoints on spell lines, for free.
  • renderAST.tsx is a React twin of the stringifier, so every emit change is made twice today. Drawing the AST viewer from the spans leaves one emitter.
  • TypeScript talks about put_on_$pile. A handful of codes get translated through the scope's method records: "a chip can't put … on (a pile)".
    • 2339, 2551, 2345, 2367, 2365, 2741, 2554
    • anything else is shown as it is, tagged as the compiler's
  • Type problems are warnings. The program is still lowered and run, as checkProp() warns and never rejects.
  • They get their own marker owner, so parse markers and type markers don't wipe each other.
  • A result that arrives after another edit is dropped. A project with parse errors isn't checked.
  • Until spans exist, each SPELL: DECLARES comment's defined: offsets map an error to its declaring statement.

Solid JSX and decorators
  • The Solid 2 plan says compiled spell can't use decorators, "blob: URL, no transpile", so hand-written and compiled classes are two spellings that MUST build the same runtime shape.
  • It plans JSX as spellCore.element() calls on hyperscript, the parser wrapping every dynamic value in a thunk.
  • A lowering step removes the reason for both: one spelling, lowered by a tool.

What JSX as JSX buys

  • Each {expression} is its own tracking scope by compilation, not by the parser wrapping thunks.
  • Tags and props are type-checked.
    • className on a <div> is an error: the React spellings left in spell sources become a to-do list.
    • <ui-*> props are typed through the JSX types augmentation.
    • The hyphenated-event trap, onUiChange against ui-change, becomes a type error.
  • No hyperscript arity trap.

What must stay true

  • Compiled spell imports ONLY @spell/…. Point the JSX compiler's helper module at @spell/core, which re-exports the helpers from the one shared Solid.
    • linkModule() already rewrites @spell/ specifiers, so no runner changes.
    • One Solid per page holds.
  • A throwing expression must not halt the page. element() was to wrap each thunk in try / catch; the compiled equivalent is a guarded effect wrapper exported by @spell/core.
  • Spell state stays cells, not signals. Nothing here touches that.

What it doesn't solve

  • A Solid component runs once. Card's to draw has a local and an early return, which would freeze. The emitter must lower statement-level control flow to <Show> and expressions, with or without TypeScript.
  • The Solid 2 research measured a decorated class constructing about 6x slower than hand-lowered accessors. A deck makes 52 cards.
    • Either our lowering turns @prop into the accessor pair itself, or compiled classes keep emitting pairs, typed.
  • Emitting Solid JSX waits for the Solid migration's runtime phases.
  • The CHECK half doesn't. Typed output with today's spellCore.element() calls and accessor pairs can be checked now, and lowered by stripping types.

/** What the editor needs from a TypeScript service.  Assumed available;  NEVER loaded by a runner. */
type TypeScriptService = {
  /** Replace the files it knows:  the emitted `.tsx`, `@spell/core`'s types, imported projects' types. */
  setFiles(files: Record<string, string>): void
  /** Type errors, as offsets into the emitted files. */
  semanticDiagnostics(): Promise<TypeScriptDiagnostic[]>
  /** Type of the expression at `offset`, in TypeScript's words, e.g. `"Card | undefined"`. */
  typeAt(file: string, offset: number): Promise<string | undefined>
  /** Plain JS:  types stripped, decorators lowered, JSX compiled for Solid, helpers imported from `moduleName`. */
  lower(files: Record<string, string>, options: { moduleName: string }): Promise<Record<string, string>>
}

/** Editor only:  runs after the spell compile, before anything is saved or run. */
async function checkAndLower(project: SP.SpellProject, service: TypeScriptService): Promise<CheckedOutput> {
  const emitted = project.emitTypeScript() // one `.tsx` per spell file, each with its node => output-range spans
  service.setFiles({
    ...emitted.files,
    "/spell-core.d.ts": SPELL_CORE_TYPES, // generated from `src/spellCore/` when the editor is built
    ...project.importedTypes() // an imported project's `<Project>.compiled.tsx`, saved beside its `.js`
  })

  const problems: SpellProblem[] = []
  for (const diagnostic of await service.semanticDiagnostics()) {
    const node = emitted.nodeAt(diagnostic.file, diagnostic.start) // innermost AST node that wrote that range
    if (node) problems.push({ match: node.match, message: inSpellWords(diagnostic, node) }) // a SPELL range
  }

  // what every runner loads:  plain ES modules which import only `@spell/...`
  const javascript = await service.lower(emitted.files, { moduleName: "@spell/core" })
  return { problems, javascript }
}

Cost and timing
  • Per keystroke: parse only, as today.
  • After the pause: emit, check, lower, save, run. A language service re-checks only the files that changed.
  • To measure before committing, as experiments beside this doc:
    • check and lower time for Solitaire, cold and warm
    • the worker's size, and what it adds to the editor's first load
    • whether Solid's compiler honours a helper module and an effect wrapper
  • Nothing is added to spell-runtime.js but the re-exported JSX helpers.

What it changes elsewhere
  • The Solid 2 rules: "compiled spell can't use decorators" and "element() thunks" get revisited there.
  • This plan: the parser's own return-type inference is dropped. Section 6's datatypes become the source of annotations.
  • File names: a .compiled.tsx beside each .compiled.js. Fixture snapshots hold the .tsx, the readable form.
  • SpellDeclarations.read() and ScopesSource read the SPELL: comments out of compiled TEXT. They read the .tsx, or the lowering keeps /*! comments.

What it does not do
  • It doesn't fix precedence. A mis-parse that happens to type-check is silent: the absolute value of x + 1 is a number either way.
  • It doesn't replace spell's own datatypes. Member lookup, typed calls and completion need answers while parsing.
  • It never runs in a runner.

11. Decisions to confirm
  1. a / an plus a known type in a signature is a parameter; the plus anything is literal.
  2. Postfix suffixes stop binding tightest: x + y is empty is isEmpty(x + y).
  3. Choice keeps "precedence, then length, then earliest". Values are normalized; the order isn't changed.
  4. A single-word property read stays permissive; a multi-word read must resolve.
  5. A typed call is rejected only on a confident mismatch: both sides known, not assignable.
  6. The declarations format gets a major version bump in phase 2.
  7. "Hard to use of in method names" is read as an argument followed by of, plus multi-word getters.
  8. Property getters become scope-changing, as later lines now read members. Editing one re-parses what follows.
  9. A datatype is stored as a string in spell's words: list of cards, choice.
  10. Exclusive lists: the wording, and whether a shared family must be said out loud.
  11. TypeScript reports, suggests and fills in types. It never overrides what the parser chose.
  12. The check lands before the Solid half, on today's JavaScript shapes.
  13. Compiled classes: @prop … accessor lowered by us, or typed accessor pairs.
  14. Fixture snapshots hold the .tsx.
