Three new ui families, <ui-include>, <ui-code> and <ui-markdown>, share one loader, UI.sources, that fetches same-origin text and saves it through a pluggable saver; highlight.js, marked and a pre-compiled spell highlighter load lazily, only when used. The page server learns to save non-HTML files, so docs pages can edit what these elements show.

Kickoff prompt

Time to create some new components!
- `<ui-include>` - import a `source` URL into the current page. Assume page is from the current server, show an error message if not. Functions kinda like Astro Islands. Build in "save" hook so we can use this in an editor soon.
- `<ui-code>` - from inline contents or `source` url, render code block in specified `language` (auto-detect if not specified). We'll also want a "spell" language formatter. Build in "save" hook for this as well. I'm thinking that "highlight.js" is a good choice for functionality -- have a quick look if there is something better.
- `<ui-markdown>` - from inline contents or `source` url, render as markdown. I'm thinking we'll use the "marked.js" package for parsing (for now) -- quickly evaluate if there is something better. We will eventually add inline editing to this. Use github markdown
- Do a quick analysis of what it would take to create a markdown parser using the spell/parser. This would live as a peer to the `spell` language.

1.4 <ui-include>
  • <ui-include source="/docs/part.html" select="main" load="visible">
  • Content goes in its shadow root by default (D14): page CSS stays out, ui tokens (inherited custom properties) still apply. page-styles renders it into the include's LIGHT DOM instead: page CSS applies, and so does <ui-root>.
  • Either way the include loads undefined ui-* families in its content itself, through RootLoader.undefinedTags(root): <ui-root> can't see into a shadow root, and a page may have no <ui-root>.
  • A whole page fetched: <body>'s children (or select's match); <head> ignored.
  • Relative href / src rewritten against source's URL.
  • Scripts don't run (D7). Nested includes load themselves; a cycle shows an error.
  • save() with select: saves that fragment by its id (PATCH /_server/page, byte-exact splice); no id: error. Without: PUT of the whole file.

1.7 Analysis: markdown parser on $/parser
  • Where: packages/markdown/ (@spell-app/markdown, $/markdown, MD), importing $/parser and $/util only; app, docs, spell may import it.
  • Fits:
    • source positions on every match (editor round-trip)
    • re-parse of a sub-range (block pass, then inline)
    • per-rule unit tests
    • Match.compile() returning HTML strings (rulex returns Rules the same way)
  • Hand-written parse() code needed:
    • tokenizer: the default one breaks markdown (// / -- start comments, <Tag is JSX, _ is a word character, ' strings span lines) -> a whitespace-preserving MarkdownTokenizer
    • container blocks (lists, quotes, lazy continuation, tab stops of 4): CommonMark's line scan, not breakIntoIndentedBlocks (one level per whitespace character)
    • emphasis (delimiter-run stack pass), link reference definitions (two passes), HTML blocks (7 start conditions), tables (the delimiter row decides)
    • no lookahead / negation; Choice parses every alternative; IncrementalParse assumes indentation
  • Effort: a useful GFM subset ~1.5-2 weeks; full CommonMark + GFM (~650 spec examples) 4-8 weeks; incremental +1-2 weeks. Speed: marked ~1 ms a doc; spell's parser ~77 ms on 259 lines.
  • Verdict: worth it if markdown must live inside spell's tooling (LSP, completion, one AST, spell-aware editing); for rendering alone, marked is ~70x faster. A todo (T5), not a phase.

C1 Auto-detect knows only a few languages

A <ui-code> with no language guesses the language, but only from a small set. Code in any other language needs language=, or it's guessed wrong or left plain.

  • The guess chooses from the "detect set", about 10 languages (CodeEngine.DETECT_SET):
    • bash, css, javascript, json, markdown
    • python, typescript, xml (which covers HTML), yaml
  • 21 more (CodeEngine.MORE: c, go, rust, sql ...) are in the same chunk, but only used when named.
  • Spell is never guessed: its bundle is too big to load on a guess.
example · 4 lines 
<!-- guessed from the detect set -->
<ui-code>const x = 1</ui-code>
<!-- named:  rust isn't guessed -->
<ui-code language="rust">let x = 1;</ui-code>
C2 Rendered markdown can't be traced back to its source

<ui-markdown> renders with marked, which keeps no source offsets. So a rendered paragraph or heading can't be mapped back to the lines it came from.

  • That matters for editing in place, later: clicking a rendered paragraph to edit its markdown.
  • A markdown parser on spell's own parser would keep positions on every match (the analysis in the Overview, 1.7; the todo, T5).
C3 Pages opened from disk can't load a source

On a page opened from disk (file://), <ui-include>, <ui-code> and <ui-markdown> can't load a source file: the browser blocks the fetch. They say so, instead of failing quietly.

  • The message: "Can't load {source}: this page was opened from disk. Open it from a web server to see it."
  • Its error kind is file-protocol (the ui-error event's kind).
  • Inline content still works.
C4 Docs bundle inlines lazy import()s: P6 must keep the engine chunks lazy or spell-ui.js grows ~50 kB C5 Spell highlight bundle is the whole parser + spell rules (likely 100s of kB): loads only for language=spell; not in auto-detect C6 Spell highlighting is accurate but slow on big files

<ui-code language="spell"> colours spell by actually parsing it, which gets keywords, types and properties right, but costs on the order of milliseconds per 100 lines.

  • It colours in two passes (SpellHighlighter.spans(), the spell highlighting decision D19):
    1. tokens: comments, text, numbers and symbols
    2. a best-effort parse, which refines those colours by each rule
  • Big files may want the first pass only ("tokenize-only"): rougher colours, no parse.

Not checked: the timing on today's parser.

C12 Regenerate the spell bundle after changing spell's grammar

The spell highlighting bundle is a generated file that's committed to the repo, so ui builds without building spell. The catch: change spell's grammar and forget to regenerate, and ui colours spell with the old grammar.

  • Regenerate: yarn gen:spell in packages/ui.
  • It writes, per language (scripts/gen-spell.ts):
    • src/languages/spell.<lang>.bundle.js
    • its type, spell.<lang>.bundle.d.ts
    • the wrapper, spell.<lang>.ts
  • Why committed: the committed-bundle decision (D15).
C13 Inline markdown in a <script> can't contain </script>

Inline markdown is best written in a <script type="text/markdown"> (or text/plain), but the text can't contain </script>: the browser ends the script there.

  • For text that needs it, load it from a file with source.
  • Or set the element's content property from code.
example · 4 lines 
<ui-markdown><script type="text/markdown">
Write `</script>` to end a script.
<!-- the browser ended the script above -->
</script></ui-markdown>
C14 Headings inside markdown join the page's outline

A # heading inside <ui-markdown> becomes a real <h1>, part of the page's heading outline, which can put it at the wrong level under the page's own headings.

  • heading-offset shifts them to fit: 1 makes # an <h2>.
  • Without it, axe's heading-order check can fail.
  • The property is headingLevelOffset, because WebKit already has a native headingOffset (D23).
example · 2 lines 
<h1>Page</h1>
<ui-markdown source="readme.md" heading-offset="1"></ui-markdown>
C15 <ui-code>'s highlighting engine is a 54 kB download

The first <ui-code> on a page loads its highlighting engine, one chunk. A page with no code never loads it.

  • Size: 54 kB gzipped.
  • In it: highlight.js, with 30 languages.
  • One chunk on purpose: a chunk per language would split Rolldown's runtime into a file every page loads (D27).
  • The docs' own copy (packages/docs/tools/_assets/lazy/code-engine.js, a classic script, D26) is 49 kB. Checked 2026-10-04: 50,390 bytes gzipped.
