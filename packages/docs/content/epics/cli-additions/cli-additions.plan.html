C1 The CLI runs whatever source is in the checkout

spell has no build step: it runs the spell packages' source straight from the checkout, through tsx. So a half-done edit in that checkout can break the spell command, and nothing tells you that's why.

  • bin/spell.mjs runs src/main.ts "from THIS checkout, through tsx", and the parser and language from the spell package beside it.
  • The risky places: a half-done change in lsp/src/, or in SpellProject.
  • Example: you're midway through renaming a method in SpellProject.ts; until it compiles again, spell check @examples fails too, with an error about your edit, not about the project.

Net effect:

  • nothing changes: an accepted limit of running from source
  • a single-file bundle (the todo below, T2) would remove it
C2 Timing an older commit borrows today's dependencies

spell speed --against <ref> also times an older commit, as "Previous". To save an install, it links today's node_modules into that commit's copy. A commit that needed different dependencies may then fail to run.

  • How it works (speedCommand.ts):
    1. git worktree add --detach puts the ref in a temp folder.
    2. Our root's and each package's node_modules are symlinked into it.
    3. The timing runner is copied in, and both trees are timed.
    4. The links are removed FIRST, then the temp worktree.
  • Example: --against HEAD~40, from before a dependency bump, may fail to load.

Net effect:

  • nothing changes: compare against recent commits, whose dependencies match today's
C3 spell format trusts the formatter to change only spaces

spell format writes whatever the language server's formatter returns straight into the .spell files, without checking it. It's safe only because that formatter changes nothing but whitespace.

  • The formatter: SpellLanguageService.formatting(), built on P.TokenFormatter (TokenFormatter.ts).
  • What keeps it whitespace-only: it copies every token exactly, and gives up (returns nothing) if the result would tokenize differently.
  • If someone later made the formatter change tokens, spell format would write that change to disk with no warning.
  • spell format never writes inside projects/test/.

Net effect:

  • nothing changes: TokenFormatter must stay whitespace-only
C4 spell repl's live screen not tried in a real terminal

spell repl has two modes. Only one of them has been run for real; the live screen you'd use in a terminal was tested only through a stand-in.

  • Piped mode (lines read from stdin): runs end to end in cli.test.ts.
  • The live screen (<ReplScreen>): tested only through ink-testing-library, in ReplScreen.test.tsx.
  • It wasn't driven in a real terminal during the night it was built.

Net effect:

  • run spell repl in a terminal once, by hand, before trusting the live screen
C5 Editing a description in spell explore

In spell explore, the e key edits a description in a one-line field. A description of several lines would be flattened by it, so e refuses those.

  • What you see instead: <name>'s description is several lines: o to edit it in your editor
  • o opens the file in your editor.
  • e never edits a test project.

Net effect:

  • nothing changes: use o for long descriptions
C6 No live reload when a project runs in the browser

spell run on a UI project opens it in your browser, served from localhost until Ctrl-C. It serves the project as compiled when the run started.

  • Edit a .spell file while it's open, and the page doesn't change.
  • To see the edit: stop the run and start it again.

Net effect:

  • nothing changes: the CLI's README.md says the same ("no live reload")
