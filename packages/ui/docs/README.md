# `@spell-app/ui` docs site

Plain, hand-authored `.html` pages in [fomantic-ui.com](https://fomantic-ui.com)'s docs style, built ONLY from
`<ui-*>` widgets:
- a left nav of every component, a masthead
- Examples / Usage / API / Theming tabs
- every example live, with its source a click away
- an "On this page" rail

More:
- Where a widget can't do what a page needs, that's a gap in the library,
  recorded in the plan doc of epic `spell-ui-pages` ([its folder](../../../../spell-app.epics/epics/spell-ui-pages/)).
- No build step to VIEW a page:  pages are static files loading ONE bundle.
  - The page server builds it when it starts, if it's stale (not committed since 2026-10-07).
- Served at `/components/ui/` by the repo's page server, live-reloading
  ([`packages/server`](../../server/), `COMPONENT_SETS`).

## A component set

- This folder is Spell UI's COMPONENT SET, laid out as every set is (epic `people-and-orgs` P18).
  - Its pages, one flat folder, tracked with the branch, so a page changes in the same commit as its element.
  - From 2026-10-05 (epic `claude-design` P6) until then, they were SHARED content:  `ui/` at the checkout's root.
- The BUILD stays beside it, in [the site folder](../site/README.md):
  - `_src/`, the bundle's entry
  - `_assets/`, the bundle
- The page server lays the build's `_assets/` over this folder at `/components/ui/`, so a page's `_assets/site.js` resolves.
  - A worktree's pages, at `/worktrees/<w>/components/ui/`, get THAT worktree's build.
- Owen COMMENTS on these pages as on every set's (epic `epic-engine`):  the bullhorns, threads, Send and the page's
  toolbar, the docs runtime's comments ALONE (spell-epic's `spell-comments.js`), drawn with the site's own Spell UI.
  - Every page loads them in its `<head>`, after the site's bundle:
    `<script defer src="/_epic/assets/spell-comments.js"></script>`.
    - `yarn site:new` writes the line (spell-epic's `templates/spell-ui-docs.html`);  a page written by hand needs it.
  - The layout loads the epics pack, `<ui-components source="/_epic/pack/epics.pack.js">`:  its `<epic-thread>` and
    `<epic-comment-pane>` draw the threads and the pane.  The site's bundle shares its Solid and Spell UI with it
    (`SitePacks.ts`).
  - Both are the epic server's engine routes (`/_epic/...`), which spell-app's page server serves too.
  - Kept in `<page>.inbox.json5` beside the page, git-ignored;  Send hands them to the standing epic `feedback`.

## Viewing

From the repo root:

```sh
spell dev server start --all                                  # starts the page server (and the editor);  prints its URL
spell dev server url "$PWD/packages/ui/docs/index.html"      # the URL of one page (starts the server if needed)
```

- Pages are `<base>/components/ui/`, `<base>/components/ui/ui-button.html` ...
- The page server reloads an open page when it, its parts, its data or the bundle changes.
- `spell dev server stop` stops it.

## Layout

```
packages/ui/docs/       (this folder, served at /components/ui/)
  index.html, getting-started.html, grammar.html, theming.html, utilities.html, icons.html, kitchen-sink.html
  components.html       the component index (cards between markers, written by `yarn site:index`)
  ui-<name>.html        one page per component family, named for its main tag;  plus a page of their own for the
                        sub-tags `pages.json5` lists under their family's `pages` (`ui-radio`, `ui-textarea`,
                        the content parts but `ui-header`)
  __parts/              layout.html:  EVERY page's chrome (top bar, nav, `<ui-root>`), written once;  footer.html
  __data/               components.json5, icons.json5, search.json5, custom-elements.json, html-custom-data.json
                        (GENERATED by `yarn site:data`, committed);  pages.json5 (hand-kept)
  examples/             files the pages' examples load (`<ui-include source>`, `<ui-markdown source>`, an icon pack)
  images/               Fomantic's docs images, same paths as fomantic-ui.com's `/images/...`

packages/ui/site/       (the build)
  _src/                 site.ts (the bundle's entry:  what's in it and why), SitePacks.ts (component packs),
                        snapshot.ts, SiteShell.ts (mounts the layout), SiteRouter.ts (swaps pages), SiteSections.ts
                        (sticky offsets, folds, landing on a hash), site.types.ts (their shared constants, which
                        `tools/SiteCheck.ts` reads too), site.css (layout glue only)
  _assets/              GENERATED, NOT committed (git-ignored since 2026-10-07;  the page server builds it):  the
                        bundle (`site.js`, `site.css`, a lazy chunk per family);  `icon-packs` is a SYMLINK to
                        `../../src/icons/icon-packs`.  NEVER edit
```

Every page loads the bundle from beside it, the page server's overlay of the site's `_assets/`:

```html
<link rel="stylesheet" href="_assets/site.css" />
<script type="module" src="_assets/site.js"></script>
```

A page's `<body>` is ONE `<main id="main" class="site-main">`, nothing else:

- First load:  `site.js` fetches [the layout](__parts/layout.html) and wraps the `main` in it (`SiteShell`).
  - THEN it defines `<ui-root display="when-ready">`,
    so the page stays hidden until the layout is in and every element is ready, and shows at once.
  - No flash of unstyled markup, no jump:  `site.css` hides the bare `main` until then (4s at most).
- Later clicks on links to other pages of the site:  `SiteRouter` fetches the page, and loads the families it uses.
  - Then it swaps only the `main`, through a `<ui-include select="main#main">`, and `pushState`s its real URL.
  - The chrome stays.
  - Back / forward, deep links and reloads work as with plain pages.
- So:  inline scripts in `main` run again on every visit (the router re-runs them),
  and `<head>` styles DON'T follow a swap.
  - Put page styles in `main`, or in the site's [layout glue](../site/_src/site.css).
- A page opened from disk (`file://`) has no bundle beside it:  view pages through the page server.
- Links are written as from the page's served address:
  - `../../` is the checkout's root
  - `../epics/epic-item.html` is another set's page

`<ui-root>` lazy-loads every other family on first use,
the doc-only `<ui-docs-*>` elements included ([`src/docs-components/`](../src/docs-components/)).
- The doc-only elements read the site data (`SiteData`, [the components data](__data/components.json5)),
  never the vocabularies.

The layout's root is `<ui-root class="site" stack-with="page" ...>`:
- stacking examples (`stackable`, `doubling`, steps, form rows, items, token tables) stack by the SCREEN,
  as on fomantic-ui.com, not by the narrower docs column
- [theming notes](../notes/theming.md), "Stacking"

The source of a page:  the site header's "open in VS Code" button.
- Pages left GitHub with the move, so they have no "edit on GitHub" link any more.

## Making a page

From `packages/ui`:

```sh
yarn site:new ui-card                                         # => packages/ui/docs/ui-card.html
yarn site:new getting-started --title "Getting started" --summary "One line."   # => packages/ui/docs/getting-started.html
```

- From [the template](../../../spell-epic/templates/spell-ui-docs.html), spell-epic's (every template is the engine's).
  - Title / summary / status from [the pages data](__data/pages.json5):  fix a summary THERE, then `yarn site:data`.
  - It refuses to overwrite (`--force`).
- A sub-tag gets a page of its own once its family's entry in `pages.json5` lists it under `pages`
  (title, summary, status).
  - Then `yarn site:data` and `yarn site:new <tag>`, which writes `<tag>.html`:
    - ONE tag's API (`<ui-docs-api tag>`, where `#<tag>` lands)
    - a Theming tab only when a family token names it
  - Its family page keeps the whole family's API, and a one-line link to it.
  - The nav, search, card index and kitchen sink follow.
- How to write one (sources, examples, usage, theming, gaps):  [the pages guide](../../../../spell-app.epics/epics/spell-ui-pages/PAGES.md).
  - The model page:  [`ui-button.html`](ui-button.html).
- Content is nested `<ui-section id header sticky collapsible dividing>`s:
  a section per topic, a section per example inside it.
  - Their titles stick below the tabs' bar (which sticks too).
  - They fold:  folds remembered per page, everything starts open.
  - Their ids spell out the nesting:  `#examples-types-emphasis` opens the Examples tab,
    unfolds what hides it, and lands its title just below the stuck ones
    ([`SiteSections`](../site/_src/SiteSections.ts)).
  - Old hashes still land (`#types`, `#emphasis`).
  - Write flat headers and headed examples, then `yarn site:sections` nests them and writes the ids.
    Rerun it after renaming a header.
- An example is a `<ui-docs-example description>` around live markup, inside its section.
  - It shows the markup's own source, re-indented, so write the markup once.
- `<ui-*>` for everything visible.
  - The site's `site.css` is layout glue only:  grid areas, widths, sticky offsets.

## Building

From `packages/ui`:

- `yarn site:build` -- after changing a vocabulary, a family sheet, an example or any source the site shows.
  - Commit [the data folder](__data/);  the bundle, `_assets/`, is git-ignored.
  - It runs:
    - `yarn site:data` -- the site data, from the vocabularies and sheets:
      - [`components.json5`](__data/components.json5) + [`icons.json5`](__data/icons.json5);  seeds `pages.json5` for a new family
      - [`search.json5`](__data/search.json5), every page's sections, for the site search, from the pages:
        rerun after renaming or moving a section
    - `yarn site:index` -- the component index's cards ([`components.html`](components.html))
    - `yarn site:kitchen` -- the kitchen sink's examples ([`kitchen-sink.html`](kitchen-sink.html)),
      from every family's `examples/elements/types.html`
    - `yarn site:bundle` -- `_assets/`, from [the site entry](../site/_src/site.ts) ([its Vite config](../vite.site.config.ts)), sizes printed
- `yarn site:dev` -- while working on the library or `_src/`:
  - `yarn site:bundle`, then the page server (started if needed) serves `/components/ui/`
  - while a Vite watch build rebuilds `_assets/` on every source edit, and the open pages reload
  - Not watched:  data, index, kitchen sink.
  - A watch rebuild leaves old hashed chunks behind:  `yarn site:build` clears them.
  - `Ctrl-C` stops the watch, not the page server.

## Checking

From `packages/ui`:  `yarn site:check <page...>` or `yarn site:check --all`.
- The command is [`site-check.ts`](../scripts/site-check.ts), on [`SiteCheck`](../tools/SiteCheck.ts).
- It loads pages from the page server in Playwright, at desktop, phone and dark, and fails on:
  - console errors, 404s
  - undefined or unrendered `ui-*` tags
  - missing tabs, an empty "On this page"
  - phone-width overflow, a nav flyout that won't open
  - a section id that doesn't follow its nesting, a flat level 2 header, a deep link that doesn't land
- Screenshots go to `tools/results/site-check/`:  LOOK at them.
