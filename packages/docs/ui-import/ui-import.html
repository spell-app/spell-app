UI Import: include, code, markdown

Three @spell-app/ui elements that show a file of this site -- a page, code, markdown -- and save it back: how they load, how saving works, and how their heavy engines stay off pages that don't need them.

Written for: people using the elements in pages, and whoever builds the editor on them Status: built on branch ui-import, 2026-10-02 Checked: unit and visual tests (chromium, firefox, webkit), and a save round-trip through the page server (see Sources) Plan and full record: the ui-import plan doc
  • <ui-include> shows another page of the site; <ui-code> highlighted code (spell included); <ui-markdown> GitHub-flavoured markdown.
  • Each takes its own text or a same-origin source, shows loading and error states, and has content / save() for an editor: one base, SourceElement, over one service, UI.sources.
  • Each family is 4-7 kB gzipped of its own code (include 4.34, code 6.94, markdown 5.05). The engines load only when a page shows code or markdown: highlight.js with 30 languages (54 kB), marked + DOMPurify (28 kB), spell's parser (138 kB, only for language="spell").
  • Saving goes through a saver the PAGE registers: ui ships none. On the page server, docs pages save text files in place (ETag-checked, so a file changed underneath is a conflict, not lost work).
  • Point source at a file of this site, or write the text inside (<script type="text/plain"> keeps it exact).
  • To save: register UI.sources.saver (docs pages have one), or cancel ui-save and save it yourself.
  • After changing spell's grammar, run yarn gen:spell in packages/ui.

The three elements on this page. Opened from disk (file://), the ones with a source say they can't load it: open this page from the page server (yarn docs:open).

  • Three families in packages/ui/src/components/: ui-include/, ui-code/, ui-markdown/. Usual layout: UI<Name>.tsx, index.ts, vocabulary, .types.ts, .css, fallback, tests, examples/ + examples/elements/, site .mdx.
  • Shared:
    • src/runtime/Sources.ts: the UI.sources service
    • src/elements/SourceElement.tsx + SourceHost.ts: base controller and host for "content from inline text or source" (content, save(), reload())
  • Lazy engine chunks, as wrapper modules (like runtime/TemporalPolyfill.ts, so Rolldown splits no shared runtime chunk):
    • ui-code/CodeHighlighter.ts -> highlight.js/lib/core + detect set
    • ui-markdown/MarkdownRenderer.ts -> marked + DOMPurify
  • Registrations per family: package.json exports + sideEffects, vite.config.ts COMPONENTS, src/index.ts, test/fallback.cases.ts, tools/demo/index.ts, yarn gen:root, docs/status.md, docs/plan.md inventory, CHANGELOG.md.
  • Content comes from, first match wins:
    1. source="url": UI.sources.load(url) -> { text, etag, url }, cached per URL (promise map, like IconPacks)
    2. a <template> child (raw < / & safe), or <script type="text/plain|markdown|...">
    3. the host's own textContent
    Inline text is dedented: common leading indent and first / last blank lines dropped.
  • Same origin only: new URL(source, document.baseURI).origin !== location.origin -> error, no fetch. file:// pages get their own message (C3).
  • While loading: <ui-loader active inline>; on failure: <ui-message state="error">. host.ready stays styles-ready; host.loaded resolves with content.
  • source changes re-fetch (previous fetch aborted); inline changes tracked by a MutationObserver (UIProgress.hostText pattern).

Built: the docs saver is spell-ui-sources.js; the server writes text files but not .json, and serves a script's fetch() raw; savers may throw { kind }.

  • host.save(text = host.content):
    1. dispatches cancelable ui-save; a listener that calls preventDefault() does the saving itself (an editor posting elsewhere)
    2. else UI.sources.save(url, text, etag) -> the registered saver (UI.sources.saver = fn). None: ui-error kind: "no-saver". Inline content with no source: updates content only
    3. success: new etag, ui-saved; 409 (file changed underneath): ui-error kind: "conflict", edits kept
  • ui ships no saver (it stands alone). The page-server saver: SPELL_SERVER.saveFile in the server's liveClient.ts, registered by packages/docs/_assets/spell-ui-sources.js; a saver that can't import SourceError throws { kind, message, status } (D28).
  • Server (D3): PageEditor's PUT /_server/page widened from .html to text files (.md, .ts, .tsx, .js, .css, .spell, .txt, .yaml, .svg; NOT .json, D25): same token, same-origin, ETag and FileLock rules. PATCH (one element by id) stays pages-only.
  • A script's fetch() (Sec-Fetch-Dest: empty) gets files AS IS, without the injected live-reload tags (D24): what an include shows and saves is the file.

3.4 <ui-include>
  • <ui-include source="/docs/part.html" select="main" load="visible">
  • Content goes in its shadow root by default (D14): page CSS stays out, ui tokens (inherited custom properties) still apply. page-styles renders it into the include's LIGHT DOM instead: page CSS applies, and so does <ui-root>.
  • Either way the include loads undefined ui-* families in its content itself, through RootLoader.undefinedTags(root): <ui-root> can't see into a shadow root, and a page may have no <ui-root>.
  • A whole page fetched: <body>'s children (or select's match); <head> ignored.
  • Relative href / src rewritten against source's URL.
  • Scripts don't run (D7). Nested includes load themselves; a cycle shows an error.
  • save() with select: saves that fragment by its id (PATCH /_server/page, byte-exact splice); no id: error. Without: PUT of the whole file.

3.5 <ui-code>

Built: highlight.js and all 30 languages are ONE lazy chunk; spell loads through a generated wrapper; loader hooks let the docs bundle load the engines as classic scripts.

  • <ui-code language="ts" source="..." line-numbers>, or inline. Shadow <pre><code class="hljs language-x">.
  • highlight.js 11.12 in ONE lazy chunk, CodeEngine (54 kB gzipped, C15): a detect set of 9 languages (ts, js, html, css, json, bash, markdown, python, yaml) to guess from, 21 more registered by name on first use. One chunk: a chunk per language would split Rolldown's runtime off (D27). CodeHighlighter.engineLoader can load it some other way (the docs' classic script, D26).
  • Colours: .hljs-* classes -> --ui-code-* tokens, light / dark; the docs' --hl-* palette, so docs pages match.
  • UI.code.register(name, hljsGrammar | (code) => spans) adds a language.
  • spell (D4), the one ui -> spell dependency, on a PRE-COMPILED bundle only:
    • packages/spell/src/highlight/: SP.SpellHighlighter.spans(text): token colours, then a best-effort parse refining them by each rule's highlightAs (D19)
    • yarn gen:spell (in ui) bundles it with esbuild (keepNames, react-dom stubbed) into COMMITTED files, packages/ui/src/languages/spell.<lang>.bundle.js and the wrapper SpellLanguage loads, spell.<lang>.ts (138 kB gzipped, C11) (D15, like icon packs): ui builds without building spell; loaded lazily when first asked for
    • language="spell" ~== spell/en; spell/es loads Spanish. No translation yet: the code stays plain, with a ui-error naming it (C7, D17)
    • not in the detect set (C5)
  • Not an editor: editing is a later epic (D12); content + save are its seam.

3.6 <ui-markdown>

Built: DOMPurify in every browser (not setHTML()), ids kept; task checkboxes labelled; the heading-offset property is headingLevelOffset.

  • <ui-markdown source="readme.md">, or inline (<script type="text/markdown"> recommended).
  • marked 18 (~14 kB), GFM on: tables, task lists, strikethrough, autolinks; footnotes later (T1).
  • Sanitized every render by DOMPurify 3.4, in every browser (D20: setHTML()'s defaults drop task checkboxes, images, heading ids and code classes), with SANITIZE_DOM off so ids survive (D21). trusted skips it. marked + DOMPurify are one lazy chunk, MarkdownEngine (28 kB gzipped).
  • Fences -> <ui-code language="x"> (D9); no info string: auto-detect.
  • Shadow DOM, GitHub-like sheet on ui tokens; heading ids are GitHub slugs, so #anchor works; relative links / images resolve against source. Task-list checkboxes are labelled by their item's text (D22); #id links scroll inside the shadow root. The heading-offset PROPERTY is headingLevelOffset (D23: WebKit has a native headingOffset).
  • Engine behind MarkdownRenderer (render(text) -> DocumentFragment, D10).

The decisions behind the design, each linked to its entry (and what was asked) in the plan doc.

  • D1 All three: highlight.js, marked, DOMPurify, each in its family's lazy chunk (Q1)
  • D3 Hook + server save: widen the page server's PUT to text files (.md, .ts, .spell ...) (Q3)
  • D4 Pre-compiled spell bundle is the ONE ui -> spell exception; language=spell is English, spell/es Spanish (Q4)
  • D5 UI.sources runtime service + shared SourceElement: one same-origin / cache / save path for all three elements
  • D6 All three render into shadow DOM
  • D7 Scripts in included HTML don't run (innerHTML); a scripts attribute later
  • D8 load="eager" default; visible / idle defer the fetch (the islands part)
  • D9 Fences in markdown render as <ui-code>: one highlighter, one palette
  • D10 Engines behind adapters (CodeHighlighter, MarkdownRenderer): swapping engines later stays local
  • D11 Language with no highlighting is named text (maps to hljs plaintext)
  • D12 Editing (code, markdown) is a later epic, by Owen's own strategy: not CodeMirror / Monaco / micromark
  • D14 <ui-include>: shadow DOM by default; page-styles renders into LIGHT DOM instead (page CSS and <ui-root> apply)
  • D15 Spell highlighter ships as a COMMITTED generated file: yarn gen:spell writes packages/ui/src/languages/spell.<lang>.js
  • D17 Unknown language, or a spell translation with no bundle: the code stays PLAIN, with a render ui-error and no message box
  • D18 spell bundles load through a literal import.meta.glob (one lazy chunk per spell.<lang>.js), not by URL: UI.code.languageBase dropped
  • D19 Spell highlighting = token colours, then a best-effort parse as a block refining them by each rule's highlightAs (SP.SpellHighlighter)
  • D20 Markdown is sanitized by DOMPurify in EVERY browser, not Element.setHTML() where it exists (Q1 said DOMPurify only where setHTML is missing)
  • D21 DOMPurify runs with SANITIZE_DOM off: heading ids like elements / forms survive (DOM clobbering can't reach a shadow root)
  • D22 Task-list checkboxes are labelled with their item's text (marked leaves them unlabelled: axe critical)
  • D23 <ui-markdown>'s heading-offset property is headingLevelOffset: WebKit's native HTMLElement.headingOffset (HTML's new headingoffset) can't be shadowed
  • D24 The page server serves a script's fetch() (Sec-Fetch-Dest: empty) the file AS IS: no injected live-reload tags
  • D25 PUT /_server/page writes text files (.md, .ts, .js, .css, .spell, .txt, .yaml, .svg ...), NOT .json; PATCH stays pages-only
  • D26 Docs pages keep the engines lazy: each is its own classic script, _assets/lazy/<name>.js, which UI's loader hooks (CodeHighlighter.engineLoader, MarkdownRenderer.engineLoader, SpellLanguage.bundleLoader) load on first use
  • D27 Each lazy engine chunk imports SourceError from runtime.types and uses it, anchoring it to core: no rolldown-runtime chunk (yarn measure's runtimeChunks)
  • D28 Savers may throw { kind, message, status } (a page's classic script can't import SourceError); UI.sources turns it into a SourceError
  • C1 Auto-detect only knows the detect set (~10 languages); others need language=
  • C2 marked keeps no source offsets: rendered nodes can't be mapped back to source through it
  • C3 file:// pages can't load source (fetch blocked): the error message says so
  • C6 Spell highlighting parses: accurate, but ~ms per 100 lines; big files may want tokenize-only
  • C7 spell/es errors until spell has a Spanish translation (none today)
  • C9 ui -> spell bundle is a documented exception to "ui never imports spell" (root AGENTS.md)
  • C10 Vite's dev server transforms fetched .ts / .css / .html (a JS module, its client script): <ui-code source> shows that under yarn dev / tests; the page server serves files raw
  • C11 spell.en.js is 469 kB minified, 138 kB gzipped (parser + rules + lodash, json5, semver, easy-state); react-dom is stubbed out of it. Loaded only for language=spell
  • C12 The spell bundle is committed: regenerate (yarn gen:spell in packages/ui) after changing spell's grammar, or ui colours with the old one
  • C13 Inline <script type=text/markdown> (or text/plain) can't contain </script>: it ends the script. Use source, or set content
  • C14 Headings inside markdown join the page outline: heading-offset fits them under the page's own (axe heading-order)
  • C15 <ui-code>'s engine chunk is 54 kB gzipped (highlight.js + 30 languages), loaded with the first code shown; the docs' copy 49 kB

6. A markdown parser on $/parser?

The analysis asked for alongside the elements: what it would take to parse markdown with spell's own parser, as a peer of the spell language. Not built; a todo.

  • Where: packages/markdown/ (@spell-app/markdown, $/markdown, MD), importing $/parser and $/util only; app, docs, spell may import it.
  • Fits:
    • source positions on every match (editor round-trip)
    • re-parse of a sub-range (block pass, then inline)
    • per-rule unit tests
    • Match.compile() returning HTML strings (rulex returns Rules the same way)
  • Hand-written parse() code needed:
    • tokenizer: the default one breaks markdown (// / -- start comments, <Tag is JSX, _ is a word character, ' strings span lines) -> a whitespace-preserving MarkdownTokenizer
    • container blocks (lists, quotes, lazy continuation, tab stops of 4): CommonMark's line scan, not breakIntoIndentedBlocks (one level per whitespace character)
    • emphasis (delimiter-run stack pass), link reference definitions (two passes), HTML blocks (7 start conditions), tables (the delimiter row decides)
    • no lookahead / negation; Choice parses every alternative; IncrementalParse assumes indentation
  • Effort: a useful GFM subset ~1.5-2 weeks; full CommonMark + GFM (~650 spec examples) 4-8 weeks; incremental +1-2 weeks. Speed: marked ~1 ms a doc; spell's parser ~77 ms on 259 lines.
  • Verdict: worth it if markdown must live inside spell's tooling (LSP, completion, one AST, spell-aware editing); for rendering alone, marked is ~70x faster. A todo (T5), not a phase.
